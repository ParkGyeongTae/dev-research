# 데이터 레이크하우스란 무엇인가

> 원문 — [What is a data lakehouse?](https://docs.databricks.com/aws/en/lakehouse/)
>
> 확인 날짜 — 2026-09-10

## 한 문장으로 말하면

데이터 레이크하우스는 **데이터 레이크의 개방적이고 저렴한 저장 방식**과 **데이터 웨어하우스의 관리·신뢰성·분석 기능**을 하나의 데이터 관리 구조에서 결합하는 아키텍처입니다.

Databricks 공식 문서는 레이크하우스를 다음과 같이 정의합니다.

> A data lakehouse is a data management system that combines the benefits of data lakes and data warehouses.
>
> **번역** — 데이터 레이크하우스는 데이터 레이크와 데이터 웨어하우스의 장점을 결합한 데이터 관리 시스템입니다.
>
> — [What is a data lakehouse?](https://docs.databricks.com/aws/en/lakehouse/) (확인: 2026-09-10)

이 정의에서 중요한 단어는 “저장소”가 아니라 **데이터 관리 시스템**입니다. 레이크하우스는 오브젝트 스토리지에 파일을 쌓아 두는 것만을 뜻하지 않습니다. 여러 작업이 같은 데이터를 읽고 쓰도록 저장 형식, 메타데이터, 처리 엔진, 거버넌스를 함께 구성하는 방식입니다.

## 왜 필요한가

데이터 레이크와 데이터 웨어하우스는 서로 다른 장점을 가졌습니다.

| 구분 | 데이터 레이크 | 데이터 웨어하우스 |
| --- | --- | --- |
| 주된 역할 | 다양한 형식의 원천 데이터를 저렴하게 보존·처리 | 정제된 구조화 데이터를 BI 쿼리에 제공 |
| 장점 | 개방형 표준 형식, 대규모 저장, ML·데이터 사이언스 활용 | 검증된 데이터, 높은 신뢰성, 분석 쿼리 최적화 |
| 반복되는 문제 | 검증되지 않은 데이터 때문에 BI에 바로 쓰기 어려움 | 독점 형식이나 별도 복사본 때문에 ML·다른 작업과 결합하기 어려움 |

Databricks 공식 문서는 레이크하우스의 목적을 서로 다른 워크로드를 위한 고립된 시스템을 피하는 것으로 설명합니다. 같은 데이터를 기반으로 BI와 머신 러닝을 수행하면 데이터 사본과 중복 비용을 줄이고, 조직의 단일 기준 데이터(single source of truth)를 만들 수 있습니다. — [What is a data lakehouse?](https://docs.databricks.com/aws/en/lakehouse/) (확인: 2026-09-10)

가장 작은 구조는 다음과 같습니다.

```text
클라우드 오브젝트 스토리지
        │
        ├─ Delta Lake: 테이블 형식·트랜잭션·스키마 관리
        ├─ Apache Spark: 대규모 배치·스트리밍 처리
        └─ Unity Catalog: 권한·계보·감사 등 거버넌스
                │
                ├─ 데이터 엔지니어링
                ├─ BI·리포팅
                └─ 머신 러닝·AI
```

이 그림은 Databricks에서 설명하는 핵심 구성의 개념도입니다. 실제 배포에서는 클라우드, 저장소 경로, Compute, 카탈로그 구성에 따라 세부 구조가 달라집니다.

## Databricks 레이크하우스는 어떻게 동작하는가

Databricks 공식 문서는 Apache Spark를 저장소와 분리된 Compute 자원에서 실행되는 확장 가능한 엔진으로 설명하고, 그 위에 Delta Lake와 Unity Catalog를 핵심 기술로 제시합니다. — [What is a data lakehouse?](https://docs.databricks.com/aws/en/lakehouse/) (확인: 2026-09-10)

### 1. 수집: 원천 데이터를 먼저 받아 둡니다

배치 또는 스트리밍 데이터가 여러 시스템과 형식에서 들어옵니다. 첫 번째 논리 계층은 데이터를 원천 형식에 가깝게 받아 두는 장소입니다.

그 데이터를 Delta 테이블로 변환하면 Delta Lake의 schema enforcement로 예상하지 못한 컬럼이나 누락된 데이터를 검사할 수 있습니다. Unity Catalog에는 조직의 거버넌스 모델과 데이터 격리 경계에 맞춰 테이블을 등록할 수 있습니다. — [What is a data lakehouse?](https://docs.databricks.com/aws/en/lakehouse/) (확인: 2026-09-10)

예를 들어 주문 이벤트가 JSON으로 들어온다면, 수집 단계에서 다음처럼 생각할 수 있습니다.

```text
주문 API·이벤트 스트림
        ↓
원천 JSON 보존
        ↓
Delta 테이블로 적재
        ↓
스키마에 맞지 않는 레코드와 변경 감지
```

이 단계의 결과는 “파일이 저장됐다”에서 끝나지 않습니다. 테이블의 스키마와 등록·접근 정책을 함께 관리하므로, 후속 정제 작업이 어떤 데이터를 읽는지 확인할 기반이 생깁니다. 반대로 원천 데이터를 바로 덮어쓰면 정제 로직이 실패했을 때 재처리할 근거가 사라질 수 있습니다.

### 2. 처리·정제: 품질을 높이며 같은 저장소에서 변환합니다

검증된 데이터는 정제·결합·새로운 특징 생성에 사용됩니다. 이후 업무 목적에 맞는 테이블로 재구성합니다. Databricks 문서는 schema-on-write와 Delta의 schema evolution을 함께 사용하면 downstream 로직을 반드시 다시 작성하지 않고도 계층의 스키마를 변경할 수 있다고 설명합니다. — [What is a data lakehouse?](https://docs.databricks.com/aws/en/lakehouse/) (확인: 2026-09-10)

실무에서 자주 쓰는 흐름을 주문 데이터에 적용하면 다음과 같습니다.

```text
Bronze: 원천 주문 이벤트를 보존
   ↓ 중복 제거·타입 변환·필수 필드 검사
Silver: 분석 가능한 주문 단위 데이터
   ↓ 업무 규칙 적용·집계
Gold: 일별 매출·고객별 주문 수 같은 소비용 데이터
```

Bronze·Silver·Gold는 레이크하우스의 필수 테이블 종류가 아니라, 데이터 품질이 점진적으로 좋아지는 계층을 나타내는 **medallion architecture** 패턴입니다. 따라서 계층 이름만 만들었다고 품질이 보장되지는 않습니다. 각 계층의 입력·출력 계약과 재처리 기준을 별도로 정해야 합니다.

### 3. 제공: 여러 소비자가 같은 데이터에서 읽습니다

마지막 계층은 정제·가공된 데이터를 사용자에게 제공합니다. 같은 데이터에 대해 BI·리포팅, 데이터 엔지니어링, 머신 러닝·AI처럼 서로 다른 작업에 맞는 데이터 레이아웃을 제공할 수 있고, Unity Catalog를 통해 원천까지 데이터 계보를 추적할 수 있습니다. — [What is a data lakehouse?](https://docs.databricks.com/aws/en/lakehouse/) (확인: 2026-09-10)

```sql
SELECT order_date, SUM(amount) AS daily_sales
FROM analytics.sales_orders
GROUP BY order_date;
```

위 SQL은 Gold 계층의 테이블을 조회하는 개념 예시이며, 이 저장소에서 실행하지 않았습니다. 실제로 실행하려면 해당 테이블과 권한, SQL 실행 환경이 필요합니다.

## 무엇이 데이터 레이크하우스를 가능하게 하는가

### Delta Lake: 파일 위에 테이블의 신뢰성을 더합니다

Databricks 공식 문서는 Delta Lake를 ACID 트랜잭션과 schema enforcement를 지원하는 최적화된 저장 계층으로 설명합니다. 이 계층이 있기 때문에 클라우드 오브젝트 스토리지의 파일을 단순히 읽는 것보다 테이블 변경을 원자적으로 관리하고, 스키마와 데이터 버전을 다루기 쉬워집니다. — [What is a data lakehouse?](https://docs.databricks.com/aws/en/lakehouse/) (확인: 2026-09-10)

핵심적인 차이는 다음과 같습니다.

```text
단순 파일 저장
  → 파일 목록과 데이터만 있음

Delta 테이블
  → 데이터 파일 + 테이블 메타데이터 + 변경 이력
```

다만 Delta 테이블을 사용한다고 모든 데이터 품질 문제가 자동으로 해결되는 것은 아닙니다. 어떤 컬럼이 필수인지, 중복을 어떻게 판정할지, 스키마 변경을 허용할지 같은 데이터 계약은 파이프라인 설계자가 정해야 합니다.

### Unity Catalog: 데이터 사용 범위를 통제합니다

Unity Catalog는 Databricks에서 데이터와 AI를 위한 통합 거버넌스 계층입니다. 테이블 접근 권한, 데이터 계보, 감사와 같은 관리 기능을 한 모델로 다룹니다. 레이크하우스의 데이터가 한곳에 모인다고 모든 사용자가 모든 데이터를 읽어도 된다는 뜻은 아닙니다. 데이터 통합과 접근 통제는 함께 설계해야 합니다. — [What is a data lakehouse?](https://docs.databricks.com/aws/en/lakehouse/) (확인: 2026-09-10)

### Apache Spark: 저장소와 분리된 처리 엔진입니다

Databricks 레이크하우스에서 Apache Spark는 클라우드 오브젝트 스토리지와 분리된 Compute 자원에서 대규모 처리를 수행합니다. 따라서 저장 데이터의 수명과 특정 Compute의 수명을 분리할 수 있습니다. 그러나 Compute 분리가 비용이나 운영을 자동으로 없애는 것은 아닙니다. 쿼리 패턴, 실행 시간, 저장 용량과 네트워크 비용을 별도로 관리해야 합니다. — [What is a data lakehouse?](https://docs.databricks.com/aws/en/lakehouse/) (확인: 2026-09-10)

## 데이터 레이크·웨어하우스와 어떻게 다른가

레이크하우스는 데이터 레이크와 데이터 웨어하우스를 단순히 한 제품 이름으로 합친 것이 아닙니다. 핵심 차이는 **개방형 표준 형식의 데이터에 최적화된 메타데이터·검증·거버넌스를 결합해 여러 사용 사례가 같은 데이터를 쓰게 하는 것**입니다. Databricks는 이를 다음 세 가지 이점으로 요약합니다. — [What is a data lakehouse?](https://docs.databricks.com/aws/en/lakehouse/) (확인: 2026-09-10)

- 표준 형식으로 저장된 데이터에 개방적이고 직접 접근할 수 있습니다.
- 머신 러닝과 데이터 사이언스에 맞춘 데이터 접근·최적화를 적용할 수 있습니다.
- BI와 고급 분석에 낮은 지연 시간과 높은 신뢰성을 제공할 수 있습니다.

따라서 “레이크하우스가 웨어하우스를 완전히 대체한다”는 문장은 환경에 따라 확인이 필요합니다. Databricks 공식 문서는 Databricks SQL을 이용한 데이터 웨어하우징도 레이크하우스의 기능을 활용한다고 설명하지만, 실제 조직의 시스템 경계·기존 제품·규제·비용 조건까지 이 문서만으로 판단할 수는 없습니다.

## 데이터 엔지니어가 놓치기 쉬운 점

레이크하우스는 저장소 하나에 데이터를 몰아넣는 전략이 아니라, 다음 경계를 함께 설계하는 방식입니다.

- **원천 보존과 정제 결과를 구분해야 합니다.** 원천에 가까운 데이터를 보존해야 실패한 변환을 재실행할 수 있습니다.
- **Delta의 스키마 검증과 데이터 품질 규칙은 다릅니다.** 전자는 스키마 불일치를 검사하지만, 업무상 유효한 금액인지·중복 주문인지까지 판단하지는 않습니다.
- **Bronze·Silver·Gold는 품질 계약이 있어야 의미가 있습니다.** 이름만 나눈 계층은 데이터 품질을 보장하지 않습니다.
- **공유 저장소가 곧 무제한 접근은 아닙니다.** Unity Catalog의 권한·격리·계보 설계를 데이터 구조와 함께 정해야 합니다.
- **여러 워크로드가 같은 데이터를 사용해도 소비 모델은 달라질 수 있습니다.** BI용 집계 테이블과 ML용 특징 데이터가 같은 원천을 공유하더라도 제공 계층의 구조는 목적에 맞게 달라집니다.

## 실행 환경

Databricks Workspace·Compute·Unity Catalog 연결이 없어 직접 실행한 명령과 출력은 없습니다. SQL과 데이터 흐름은 공식 문서의 동작을 설명하기 위한 미실행 예시입니다.

## 확인하지 못한 것

- 이 문서의 SQL과 Delta 동작을 실제 Databricks Runtime에서 재현하지 못했습니다 — 이 환경에 Databricks 계정과 Compute 연결이 없습니다.
- 특정 클라우드의 성능·요금·네트워크 구성은 확인하지 않았습니다 — 공식 문서의 공통 아키텍처 설명만 다뤘으며, 해당 값은 배포 환경과 시점에 따라 달라집니다.
