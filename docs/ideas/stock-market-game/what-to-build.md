# 가상 주식 게임의 첫 버전은 무엇을 만들까요?

**가상 기업과 뉴스를 바탕으로 투자 결정을 내리고, 결과를 복기하는 짧은 턴제 전략 게임을 구상합니다.** 웹과 앱에서 같은 게임 규칙을 사용하고, 화면은 각 환경에 맞게 개발하는 방향입니다.

이 문서는 초기 기획입니다. 가상 시장으로 개발하고 웹과 앱을 함께 고려한다는 대화의 방향을 기록합니다. 대상 사용자, 기업 수, 턴 수, 로그인 정책, 기술 구성의 세부 사항은 검증 전인 제안이며, 출시나 수익성을 확인한 결과가 아닙니다.

## 어떤 경험을 제공하려고 하나요?

이 문서에서 말하는 가상 주식 게임은 기업·뉴스·화폐·가격 변화 규칙을 직접 설계하는 게임입니다. 현실의 주가나 실제 주문 체결을 재현하는 정확도를 목표로 삼지는 않습니다. 게임에서 얻은 수익률로 현실의 투자 능력을 평가하지도 않습니다.

**가설 — 대상 사용자:** 주식이라는 소재에 관심이 있고, 제한된 정보로 선택한 뒤 그 결과를 확인하는 짧은 전략 게임을 즐기는 사람을 첫 대상으로 생각합니다. 주식 경험의 유무에 따라 규칙 이해가 얼마나 달라지는지는 확인이 필요합니다.

**가설 — 제공할 가치:** 서로 충돌하는 정보를 비교하고, 조사할 대상과 투자할 대상을 선택하며, 다음 판에서 다른 판단을 시도하는 재미입니다. 뉴스 요약이나 투자 답변 생성만으로 이 플레이 경험이 대체되지는 않을 것이라는 기획상 판단입니다. AI가 구현하거나 플레이할 수 없다는 주장은 아닙니다.

첫 시제품에서는 다음 흐름을 한 판 안에 완성하도록 제안합니다.

```text
이번 턴 뉴스 확인
→ 기업 정보 확인 및 제한된 추가 조사
→ 매수·매도·현금 보유 결정
→ 턴 종료와 사건 처리
→ 가격·보유 자산 변화 확인
→ 마지막 턴 종료 후 판단 복기
```

## 최소 상황으로 재미를 어떻게 확인하나요?

**설계 예시:** 가상 항공사·정유사·여행사가 있고, 여행 수요 증가와 연료 공급 문제가 같은 시기에 발생합니다. 플레이어는 제한된 조사 기회를 항공사의 비용 구조에 쓸지, 여행사의 예약 상황에 쓸지 선택합니다.

뉴스는 판단할 단서를 제공하지만 다음 가격을 확정해서 알려주지는 않도록 설계합니다. 기업 상태와 사건이 결과에 영향을 주고, 플레이어가 볼 수 있는 정보의 범위를 별도로 정하는 방식입니다. 정확한 계산식과 불확실성을 넣는 방식은 아직 정하지 않았습니다. 이 예시의 관계는 게임 규칙이며 현실의 주가 변화에 대한 설명이 아닙니다.

| 설계 조건 | 플레이에서 확인할 결과 | 실패 증상 |
| --- | --- | --- |
| 기업마다 사건의 영향이 다릅니다 | 같은 뉴스에서도 여러 투자 선택을 검토합니다 | 긍정적인 뉴스에 해당하는 종목만 사면 항상 유리합니다 |
| 정보가 제한되고 추가 조사에는 기회비용이 있습니다 | 어느 정보를 더 확인할지 고민합니다 | 조사하지 않아도 되거나 모든 정보를 비용 없이 확인합니다 |
| 결과에 영향을 준 요인을 복기할 수 있습니다 | 실패 이유와 다음 시도에서 바꿀 점을 설명합니다 | 가격이 이유 없이 바뀌었다고 느끼고 재도전할 근거를 찾지 못합니다 |

**판단:** 처음에는 기업과 사건의 수보다 이 선택과 복기의 흐름을 확인하겠습니다. 난수만으로 가격을 바꾸거나, 뉴스 한 줄이 매매의 정답이 되는 구조는 초기 설계에서 피하려고 합니다. 실제 재미는 플레이테스트로 확인해야 합니다.

## 첫 시제품의 범위는 어디까지인가요?

다음 수치는 작업 범위를 제한하기 위한 **초기 제안**이며, 적정 분량을 측정한 결과가 아닙니다.

| 항목 | 제안 범위 | 확인하려는 것 |
| --- | --- | --- |
| 시장 | 가상 기업 5개, 산업 2개 | 기업 사이의 차이와 관계를 이해할 수 있는지 |
| 진행 | 기본 시나리오 1개, 12턴 | 한 판 안에서 선택·결과·복기를 경험하는지 |
| 행동 | 매수·매도·현금 보유, 제한된 추가 조사 | 행동마다 선택할 이유가 있는지 |
| 화면 | 뉴스, 기업 상세, 주문, 보유 자산, 결과 복기 | 설명을 최소화해도 진행할 수 있는지 |
| 플레이 형태 | 싱글플레이 | 다른 참가자 없이 핵심 재미가 성립하는지 |
| 저장 | 현재 기기의 진행 저장 | 중단했다가 같은 기기에서 이어 할 필요가 있는지 |

멀티플레이, 온라인 순위, 실시간 시세 연동, 다수의 시나리오, 유료 상품은 첫 재미 검증 범위에 포함하지 않는 제안입니다. 로그인과 계정 동기화는 핵심 플레이를 확인한 뒤 추가하는 순서를 권합니다.

## 웹과 앱은 어떻게 나누나요?

현재 기술 선택의 검토 기준은 **웹 Next.js, 앱 React Native + Expo, 공통 게임 규칙 TypeScript**입니다. 실제 프로젝트와 의존성 버전은 아직 정하지 않았습니다.

| 부분 | 제안 구성 | 공유 경계 |
| --- | --- | --- |
| 웹 화면 | Next.js + React | 뉴스·주문·차트 등 상호작용 화면을 Client Components로 구성합니다 |
| iOS·Android 화면 | React Native + Expo | 앱의 화면 전환과 터치 흐름을 별도로 구현합니다 |
| 게임 규칙 | 독립된 TypeScript 코드 | 기업 상태, 사건 처리, 매매와 턴 진행을 웹과 앱에서 공유합니다 |
| 콘텐츠와 저장 형식 | 공통 데이터 정의 | 기업·시나리오와 저장 데이터의 구조를 함께 관리합니다 |
| 계정 기능 | 웹과 앱이 호출하는 서버 API | 계정 기록 보관과 동기화를 추가할 때 사용합니다 |

Next.js 공식 문서는 상태·이벤트 처리·브라우저 API가 필요한 경우 Client Components를 사용하도록 안내합니다. 이 게임의 주문 입력과 턴 진행 화면에 적용할 근거입니다. — [Next.js — Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components) (공식 문서 표시 버전: 16.4.3)

Expo 공식 튜토리얼은 React Native와 Expo로 Android·iOS·웹에서 동작하는 앱을 만드는 구성을 제공합니다. 이 기획에서는 웹에 Next.js를 검토하고 있으므로, Expo 앱의 화면과 Next.js 화면을 별도로 설계하는 제안입니다. — [Expo — Tutorial: Using React Native and Expo](https://docs.expo.dev/tutorial/introduction/) (판번호 없는 공식 안내, 적용 SDK 버전 미정)

게임 규칙 코드는 React, 브라우저 저장소, 기기 API에 직접 의존하지 않게 구성하도록 제안합니다. 예를 들어 같은 게임 상태와 플레이어 선택, 같은 사건 입력을 전달하면 웹과 앱에서 같은 다음 상태를 계산하는 구조입니다. 저장과 로그인 연결은 플랫폼별 처리로 분리합니다. 이는 구현을 완료한 구조가 아니라 향후 개발 지침입니다.

**성능 판단:** React Native + Expo를 선택했다는 사실만으로 더 부드러운 화면이 보장되지는 않습니다. React Native 공식 성능 문서는 JavaScript의 과도한 작업으로 터치 반응과 애니메이션이 지연될 수 있으며, 성능은 출시용 빌드에서 확인해야 한다고 설명합니다. — [React Native — Performance Overview](https://reactnative.dev/docs/performance) (판번호 없는 공식 안내, 적용 React Native 버전 미정)

**미실행:** 이 게임의 뉴스 스크롤, 차트 조작, 주문창 전환, 턴 종료 후 화면 갱신을 실제 기기에서 측정하지 않았습니다. 차트 라이브러리와 렌더링 구조를 정하지 않았으므로 Capacitor 등 다른 방식보다 부드럽다고 단정하지 않습니다.

## 로그인은 언제 제안하나요?

**정책 제안:** 기본 시나리오는 비회원도 끝까지 플레이하고 다시 시도하게 합니다. 회원 여부에 따른 시작 자금·정보량·가격 계산의 차이는 두지 않고, 로그인은 계정에 기록을 보관하거나 웹과 앱에서 이어 하려는 시점에 제안합니다.

```text
바로 시작
→ 기본 시나리오 완주 및 복기
→ 다시 플레이하거나 로그인하고 계정에 기록 보관
```

비회원 화면에는 저장 범위를 “현재 기기에 저장”으로 안내하도록 제안합니다. 로그인할 때는 기존 플레이 기록을 이어서 보관해야 하며, 이미 기록이 있는 계정으로 로그인하는 경우의 병합·선택 규칙은 아직 정하지 않았습니다.

중요한 계정 기반 기능이 없는 앱은 로그인 없이 사용할 수 있게 하라는 Apple의 지침도 이 방향을 검토할 근거입니다. 이 문서의 정책이 심사 통과를 보장하지는 않습니다. — [Apple — App Review Guidelines, 5.1.1(v) Account Sign-In](https://developer.apple.com/app-store/review/guidelines/#data-collection-and-storage) (판번호 없는 공식 지침)

## 무엇을 확인하고 다음 개발을 결정하나요?

현재는 **시제품을 만들어 핵심 재미를 검증할 단계**로 판단합니다. 첫 플레이테스트에서는 다음 행동을 관찰하도록 제안합니다.

1. 설명을 최소화했을 때 뉴스 확인부터 턴 종료까지 진행할 수 있는지 봅니다.
2. 어떤 정보를 근거로 투자했는지 듣습니다.
3. 손실이 났을 때 결과의 이유와 다음에 바꿀 선택을 설명할 수 있는지 확인합니다.
4. 권유하지 않아도 다시 시작하는지 관찰합니다.
5. 웹과 앱에서 조작이 막히거나 진행 저장이 실패하는 지점을 기록합니다.

재도전은 초기 재미의 단서로 해석하고, 유료 구매 의사와 구분하겠습니다. 반복 사용과 지불 의사는 실제 사용자 검증이 필요합니다. 통과 기준 수치와 수익 모델은 아직 정하지 않았습니다.

## 확인하지 못한 것

- **대상 사용자와 수요 — 확인 필요:** 사용자 인터뷰와 플레이테스트를 하지 않아 주식 초보자와 전략 게임 이용자 중 누구에게 더 적합한지 확인하지 못했습니다.
- **게임 규칙과 균형 — 미실행:** 가격 계산, 사건의 발생 방식, 조사 비용과 턴 수를 구현하거나 실험하지 않았습니다.
- **웹·앱 구현과 성능 — 미실행:** 제품 프로젝트를 생성하지 않았고 실제 기기에서 차트·화면 전환·복귀 후 진행 복구를 검증하지 않았습니다.
- **계정과 저장 — 확인 필요:** 인증 제공자, 저장소, 비회원 기록의 계정 이전, 동시 저장 충돌 처리 방식을 정하지 않았습니다.
- **출시와 수익성 — 확인 필요:** 유통 경로별 출시 절차, 유료화 방식, 구매 의사와 운영 비용을 검증하지 않았습니다.
