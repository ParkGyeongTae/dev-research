# Claude Code 베스트 프랙티스

> **원문** [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices) (code.claude.com/docs/en/best-practices)<br/>
> **확인 날짜** 2026-09-05 — 원문에 판번호도 최종 수정일 표기도 없습니다<br/>
> **검증 상태** 원문을 읽고 정리한 문서입니다. 직접 확인한 것은 그렇게 표시했고, 나머지는 **원문에서 읽은 것**입니다.<br/>
> **확인 환경** `claude --version` → **2.1.236 (Claude Code)**, macOS (Darwin 24.6.0)

## 이 문서 전체를 지배하는 전제 하나

원문은 권장사항을 나열하기 전에 **모든 권장이 하나의 제약에서 나온다**고 못 박습니다.

> "Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills."

이걸 놓치면 나머지가 그냥 팁 목록으로 읽힙니다. `/clear`도, 서브에이전트도, plan mode도 전부 **컨텍스트 예산을 지키는 서로 다른 방법**입니다. 어떤 권장을 적용할지 고를 때 "이게 내 컨텍스트를 아끼나?"를 기준으로 삼으면 판단이 빨라집니다.

## 1. 검증 수단을 먼저 쥐여준다

원문이 가장 앞에 두는 항목입니다. 근거가 명확합니다 — **Claude는 "다 된 것처럼 보일 때" 멈추고**, 돌릴 수 있는 검사가 없으면 그 판단의 유일한 근거가 "보이기에"가 됩니다. 그러면 검증 루프가 사람이 됩니다.

검사는 대화 안에서 읽을 수 있는 신호면 무엇이든 됩니다 — 테스트 스위트, 빌드 종료 코드, 린터, 출력을 픽스처와 비교하는 스크립트, 디자인과 대조할 스크린샷.

검사를 만든 다음, **얼마나 강하게 종료를 막을지**를 고릅니다. 원문은 네 단계로 제시합니다.

| 방법 | 강제력 | 준비 비용 |
| --- | --- | --- |
| 한 프롬프트 안에서 "검사를 돌리고 반복하라"고 지시 | 약함 | 없음 |
| `/goal` 조건으로 설정 — 별도 평가자가 매 턴 재확인 | 중간 | 낮음 |
| **Stop 훅** — 검사를 스크립트로 돌려 턴 종료를 차단 | 강함 | 중간 |
| 검증 서브에이전트 / 워크플로 — 다른 모델이 결과를 반박 | 강함 | 중간 |

:::note 원문에 명시된 한계
Stop 훅은 무한정 막지 않습니다. **연속 8회 차단되면 Claude Code가 훅을 무시하고 턴을 끝냅니다.** 훅을 "절대 뚫리지 않는 게이트"로 설계하면 안 되는 이유입니다.
:::

원문은 성공을 **주장**하지 말고 **증거**를 내놓게 하라고 덧붙입니다 — 테스트 출력, 실행한 명령과 반환값, 결과 스크린샷. 안 보고 있던 세션에도 그대로 통하기 때문입니다.

## 2. 탐색 → 계획 → 구현 → 커밋

바로 코딩에 들어가면 **엉뚱한 문제를 푼 코드**가 나옵니다. 원문은 plan mode로 탐색과 실행을 분리하라고 권합니다.

1. **탐색** — `Shift+Tab`으로 plan mode 진입(또는 `claude --permission-mode plan`). 파일을 읽고 답만 하며 변경하지 않습니다
2. **계획** — 구현 계획을 만들게 합니다. `Ctrl+G`로 계획을 에디터에서 직접 고칠 수 있습니다
3. **구현** — 계획을 승인하거나 `Shift+Tab`으로 빠져나와 실행
4. **커밋**

:::warning 원문이 직접 밝히는 경계
plan mode는 **오버헤드이기도 합니다.** 오타 수정, 로그 한 줄 추가, 변수 이름 변경처럼 범위가 분명하고 작은 일은 그냥 시키라고 합니다.

기준 문장이 정확합니다 — **"If you could describe the diff in one sentence, skip the plan."**
:::

계획이 값어치를 하는 건 접근 방식이 불확실할 때, 여러 파일을 건드릴 때, 고치는 코드가 낯설 때입니다.

## 3. 프롬프트에 구체적인 맥락을 넣는다

Claude는 의도를 추론할 수는 있어도 읽어낼 수는 없습니다. 원문의 개선 예시는 네 갈래입니다.

| 전략 | 나쁜 예 | 좋은 예 |
| --- | --- | --- |
| **범위를 좁힌다** | "add tests for foo.py" | "foo.py에서 **로그아웃 상태 엣지 케이스**를 다루는 테스트를 써라. mock은 쓰지 마라" |
| **출처를 가리킨다** | "이 API가 왜 이렇게 이상하지?" | "`ExecutionFactory`의 **git 히스토리를 훑어서** API가 어떻게 이렇게 됐는지 요약해라" |
| **기존 패턴을 가리킨다** | "캘린더 위젯 추가해줘" | "홈페이지의 기존 위젯 구현을 보고 패턴을 파악해라. `HotDogWidget.php`가 좋은 예다. 그 패턴을 따라…" |
| **증상을 설명한다** | "로그인 버그 고쳐줘" | "세션 타임아웃 후 로그인이 실패한다. `src/auth/`의 토큰 갱신을 봐라. **재현하는 실패 테스트를 먼저 쓰고** 고쳐라" |

:::note 반대 방향도 원문에 있습니다
모호한 프롬프트가 쓸모 있을 때가 있습니다 — 탐색 중이고 방향을 틀 여유가 있을 때입니다. `"what would you improve in this file?"` 같은 질문은 **물어볼 생각조차 못 했던 것**을 끌어냅니다.
:::

맥락을 넣는 통로는 `@` 파일 참조, 이미지 붙여넣기, URL(`/permissions`로 자주 쓰는 도메인 허용), 파이프(`cat error.log | claude`), 그리고 Claude가 직접 가져오게 시키는 것입니다.

## 4. 환경을 설정한다

### CLAUDE.md

매 대화 시작에 읽히는 파일입니다. `/init`으로 초안을 만들고, `/context`로 실제 로드됐는지 확인합니다.

원문의 이 절은 요약본입니다 — **위치와 로드 순서, 200줄 크기 기준, `.claude/rules/`, 지시가 안 먹힐 때의 진단**은 별도 페이지인 [How Claude remembers your project](https://code.claude.com/docs/en/memory)에 있습니다.

원문이 강조하는 건 **넣을 것보다 뺄 것**입니다.

| 넣는다 | 뺀다 |
| --- | --- |
| Claude가 짐작할 수 없는 Bash 명령 | 코드를 읽으면 알 수 있는 것 |
| 기본값과 다른 코드 스타일 규칙 | 이미 아는 표준 관례 |
| 테스트 방법과 선호하는 러너 | 상세 API 문서(링크만) |
| 저장소 예절(브랜치 명명, PR 관례) | 자주 바뀌는 정보 |
| 이 프로젝트만의 아키텍처 결정 | 긴 설명과 튜토리얼 |
| 개발 환경의 특이점(필수 환경 변수) | "깨끗한 코드를 써라" 같은 자명한 것 |

판정 기준 한 줄: **"이 줄을 지우면 Claude가 실수하게 되나?"** 아니면 자르라고 합니다.

증상별 진단도 명시돼 있습니다.

- **규칙이 있는데도 계속 어긴다** → 파일이 너무 길어서 그 규칙이 묻힌 것입니다
- **CLAUDE.md에 답이 있는 걸 되묻는다** → 표현이 모호한 것입니다
- 한 줄만 `IMPORTANT`로 강조하면 통하지만, **여러 줄을 강조하면 아무것도 안 두드러집니다**

`/doctor`를 돌리면 코드베이스에서 유추 가능한 내용을 잘라내자고 제안해 줍니다. `@path/to/import` 문법으로 다른 파일을 가져올 수 있습니다.

:::tip 이 저장소에서 확인한 것
이 저장소는 `CLAUDE.md`를 `AGENTS.md`의 **심볼릭 링크**로 두고 있습니다. Claude Code와 다른 에이전트가 같은 지침 파일을 읽게 하면서 내용이 두 벌로 갈라지지 않게 하는 방법입니다 — 실제로 이 세션에서 링크 너머의 `AGENTS.md`가 지침으로 로드되는 것을 확인했습니다.
:::

### 권한

Pro·Max·Team 플랜의 대화형 터미널·VS Code 세션은 **auto 모드**가 기본입니다 — 별도 분류 모델이 대부분의 행동을 대신 검토하고, 범위 확대·미확인 인프라·적대적 콘텐츠에 유도된 행동처럼 위험해 보이는 것만 막습니다.

다른 플랜의 기본인 **Manual 모드**는 시스템을 바꿀 수 있는 행동마다 물어봅니다. 안전하지만 원문 표현대로 **"열 번째 승인쯤부터는 검토가 아니라 클릭"**이 됩니다. 두 가지로 줄입니다.

- **허용 목록** — `npm run lint`, `git commit`처럼 안전한 걸 미리 승인 (`/permissions`)
- **샌드박스** — OS 수준으로 파일·네트워크 접근을 제한 (`/sandbox`)

### 확장 수단 — 무엇을 언제 쓰나

| 수단 | 성격 | 언제 |
| --- | --- | --- |
| **CLI 도구** (`gh`, `aws`, `gcloud`) | 컨텍스트 효율이 가장 높음 | 외부 서비스와 상호작용할 때 **1순위** |
| **MCP 서버** (`claude mcp add`) | 외부 도구 연결 | Notion·Figma·DB 등 CLI가 없을 때 |
| **훅** (`.claude/settings.json`, `/hooks`) | **결정적** | 예외 없이 매번 일어나야 하는 일 |
| **스킬** (`.claude/skills/SKILL.md`) | 필요할 때만 로드 | 가끔만 필요한 도메인 지식·워크플로 |
| **서브에이전트** (`.claude/agents/*.md`) | 별도 컨텍스트 | 파일을 많이 읽거나 전문적 집중이 필요한 작업 |
| **플러그인** (`/plugin`) | 위를 묶은 배포 단위 | 커뮤니티·공식 배포본 |

원문이 명확히 구분하는 지점: **CLAUDE.md의 지시는 권고(advisory)이고 훅은 결정적(deterministic)입니다.** "반드시"가 필요하면 CLAUDE.md에 세게 쓰는 게 아니라 훅으로 내려야 합니다.

스킬과 CLAUDE.md의 분담도 명시돼 있습니다 — CLAUDE.md는 **매 세션 로드되므로 넓게 적용되는 것만**, 가끔 필요한 것은 스킬로. 부작용이 있어 수동으로만 부르고 싶은 워크플로는 `disable-model-invocation: true`를 씁니다.

## 5. 세션을 관리한다

### 빨리, 자주 방향을 튼다

- `Esc` — 실행 중단, 컨텍스트는 보존
- `Esc Esc` 또는 `/rewind` — 이전 대화·코드 상태로 복원, 또는 선택 지점부터 요약
- `"Undo that"` — 변경 되돌리기
- `/clear` — 관련 없는 작업 사이에 컨텍스트 초기화

기준선이 구체적입니다 — **같은 문제로 두 번 넘게 고쳐줬다면** 컨텍스트가 실패한 접근들로 오염된 것입니다. `/clear`하고 배운 걸 반영한 더 구체적인 프롬프트로 새로 시작하는 편이 거의 항상 낫습니다.

### 컨텍스트를 적극적으로 관리한다

- 작업 사이 `/clear`
- 한도에 가까워지면 자동 압축이 돌며 코드 패턴·파일 상태·핵심 결정을 남깁니다
- `/compact <지시>` — 압축 방향을 지정 (`/compact Focus on the API changes`)
- `Esc Esc` → 체크포인트 선택 → **Summarize from here**(이후를 압축) / **Summarize up to here**(이전을 압축)
- CLAUDE.md에 압축 지침을 넣어 매번 살릴 것을 지정할 수 있습니다
- `/btw` — 컨텍스트에 남지 않는 곁가지 질문

### 체크포인트

프롬프트를 보낼 때마다 체크포인트가 생기고, 파일은 변경 전에 스냅샷됩니다. 덕분에 **위험한 시도를 그냥 시켜보고 안 되면 되돌리는** 방식이 가능해집니다.

:::danger 원문의 Warning — 반드시 알아야 할 한계
체크포인트는 **Claude의 파일 편집 도구를 거친 변경만** 추적합니다. **Bash 명령이나 외부 프로세스로 생긴 변경은 잡히지 않습니다.**

> "This isn't a replacement for git."

이 저장소처럼 `sed`·heredoc으로 파일을 고치는 흐름에서는 체크포인트가 그 변경을 되돌려주지 않습니다. git 커밋이 유일한 안전망입니다.
:::

### 세션 재개

`claude --continue`로 이어가고 `claude --resume`으로 골라 들어갑니다. `/rename`으로 이름을 붙여 **브랜치처럼** 다루라고 권합니다 — 작업 흐름 하나에 세션 하나.

## 6. 자동화하고 늘린다

### 비대화형 모드

`claude -p "프롬프트"`로 CI·pre-commit 훅·스크립트에 넣습니다. 출력 형식은 세 가지입니다.

```bash
claude -p "Explain what this project does"                          # 평문
claude -p "List all API endpoints" --output-format json             # result 필드를 가진 JSON 객체 하나
claude -p "Analyze this log file" --output-format stream-json --verbose  # 줄마다 JSON 객체
```

`-p` 실행도 재개 가능한 세션을 만듭니다 — 원치 않으면 `--no-session-persistence`를 붙입니다.

### 병렬 세션

| 방식 | 성격 |
| --- | --- |
| Worktrees | 격리된 git 체크아웃에서 편집 충돌 없이 |
| 세션 간 메시징 | 직접 띄운 세션끼리 결과 전달 |
| 데스크톱 앱 | 여러 로컬 세션을 시각적으로 관리 |
| Claude Code on the web | 클라우드 실행 |
| Agent view (`claude agents`) | **research preview** |
| Agent teams | **experimental, 기본 비활성** |

원문이 강조하는 건 속도만이 아닙니다. **새 컨텍스트는 코드 리뷰를 개선합니다** — 방금 자기가 쓴 코드에 편향되지 않기 때문입니다. Writer/Reviewer 패턴(세션 A가 구현, 세션 B가 리뷰, 피드백을 A에 전달)이 예로 나옵니다.

### 팬아웃

git 저장소에서 `/batch <지시>`를 돌리면 변경을 **5~30개 서브에이전트로 쪼개고** 각자 워크트리에서 작업해 PR을 엽니다. 직접 스크립트로 몰고 싶으면 `claude -p`를 반복합니다.

```bash
for file in $(cat files.txt); do
  claude -p "Migrate $file from Python 2 to Python 3. Return OK or FAIL." \
    --allowedTools "Edit,Bash(git commit *)"
done
```

원문의 순서가 중요합니다 — **먼저 2~3개 파일로 돌려 프롬프트를 다듬고**, 그 다음 전체에 겁니다. 무인 실행에서는 `--allowedTools`로 할 수 있는 일을 좁히는 게 핵심입니다.

### 적대적 리뷰 단계

무인으로 오래 돌수록 독립적인 검사가 중요해집니다. 새 서브에이전트 컨텍스트의 리뷰어는 **변경을 만든 추론 과정을 못 보고 diff와 기준만 봅니다.** 그래서 결과를 그 자체로 평가합니다. 버그 검사는 `/code-review` 스킬이, 계획 대비 검사는 직접 쓴 리뷰 프롬프트가 맡습니다.

:::warning 원문이 붙인 경고
**"A reviewer prompted to find gaps will usually report some, even when the work is sound, because that is what it was asked to do."**

지적을 전부 쫓으면 과잉 설계로 갑니다 — 불필요한 추상화 계층, 방어 코드, 일어날 수 없는 경우의 테스트. 리뷰어에게 **정확성이나 명시된 요구사항에 영향을 주는 것만** 보고하라고 지시하고 나머지는 선택으로 다루라고 합니다.
:::

## 원문의 마지막 절 — "패턴은 고정된 게 아니다"

이 페이지는 벤더 문서치고 **"하지 말라"가 많고**, 그 태도가 마지막 절에서 가장 분명해집니다. 원문은 컨텍스트를 쌓아야 할 때, 계획을 건너뛰어야 할 때, 모호하게 물어야 할 때가 각각 있다고 인정하고, **무엇이 통했는지 관찰해 직관을 기르라**로 끝냅니다.

앞 절들에서 하나씩 본 단서들이 여기로 모입니다 — plan mode는 한 문장으로 diff를 설명할 수 있으면 건너뛰고, Stop 훅은 연속 8회 차단되면 무시되며, 체크포인트는 Bash 변경을 못 잡고, 적대적 리뷰어는 시키면 없는 문제도 만들어 옵니다. **어느 것도 항상 켜 두라는 권장이 아닙니다.**

## 실패 패턴 다섯

원문의 "Avoid common failure patterns" 절입니다. 증상 → 처방 구조가 그대로 있어 그대로 옮깁니다.

| 패턴 | 증상 | 처방 |
| --- | --- | --- |
| **잡탕 세션** | 한 작업 하다 딴 걸 묻고 다시 돌아옴 | 관련 없는 작업 사이에 `/clear` |
| **반복 교정** | 고쳐줘도 계속 틀림 | **두 번 실패하면** `/clear` 후 배운 걸 반영해 새 프롬프트 |
| **과잉 CLAUDE.md** | 너무 길어 절반을 무시함 | 가차 없이 쳐낸다. 시키지 않아도 하는 건 지우거나 훅으로 |
| **믿고 검증 안 함** | 그럴듯한데 엣지 케이스를 놓침 | 항상 검증 수단을 준다. **검증 못 하면 배포하지 않는다** |
| **무한 탐색** | 범위 없는 "조사해봐"로 수백 파일을 읽음 | 범위를 좁히거나 서브에이전트에 맡긴다 |

## 읽고도 놓치기 쉬운 지점

여기부터는 **원문에 그대로 있는 말이 아니라 정리하며 든 판단**입니다.

- **"권고와 결정적 강제"의 구분이 이 문서의 진짜 뼈대입니다.** CLAUDE.md·프롬프트·계획은 전부 권고고, 훅과 `--allowedTools`만 강제입니다. 그런데 사람은 CLAUDE.md에 대문자로 쓰면 강제라고 착각합니다. 원문이 "여러 줄 강조하면 아무것도 안 두드러진다"고 말하는 게 그 지점입니다.
- **체크포인트 경고는 이 저장소에 바로 걸립니다.** 이 세션에서 문서를 `sed`와 heredoc으로 고쳤는데, 그 변경은 체크포인트로 되돌릴 수 없습니다. 편집 도구를 쓸지 Bash를 쓸지가 되돌리기 가능성을 바꾼다는 뜻입니다.
- **`/clear` 기준선이 "두 번"이라는 게 구체적입니다.** 대부분 그보다 훨씬 오래 끕니다. 세 번째 교정을 하고 있다면 이미 늦은 것입니다.
