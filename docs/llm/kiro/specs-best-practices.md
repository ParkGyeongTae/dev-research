# Kiro 스펙 베스트 프랙티스

> **원문** [Best practices](https://kiro.dev/docs/specs/best-practices/) (kiro.dev/docs/specs/best-practices/)<br/>
> **원문 최종 수정** August 4, 2026 — 세 문서 중 유일하게 날짜 표기가 있습니다<br/>
> **확인 날짜** 2026-09-05<br/>
> **검증 상태** 원문을 읽고 정리한 문서입니다. **Kiro를 직접 써보지 않았습니다** — 동작을 재현해 확인한 것은 하나도 없습니다.

:::info 이 문서의 범위 — 도구 전반이 아닙니다
Kiro는 **IDE·CLI·Web·Mobile**을 가진 플랫폼이고, 원문은 그중 **specs 기능 하나**에 대한 페이지입니다(`/docs/specs/best-practices/`). "Kiro를 잘 쓰는 법" 전반이 아니라 **"스펙을 잘 쓰는 법"**입니다.

파일명을 `best-practices.md`가 아니라 `specs-best-practices.md`로 둔 이유도 이것입니다 — 나중에 다른 영역의 베스트 프랙티스를 정리해도 섞이지 않게 하기 위해서입니다.
:::

## 스펙이 무엇인가

Kiro의 스펙은 **요구사항·설계·작업 항목을 파일로 문서화하는 체계**입니다. 스펙 하나가 폴더 하나이고, 그 안에 세 파일이 생깁니다.

| 파일 | 담는 것 |
| --- | --- |
| `requirements.md` | 무엇을 만들 것인가 |
| `design.md` | 어떻게 만들 것인가 |
| `tasks.md` | 실행 단위로 쪼갠 작업 목록 |

저장 위치는 `.kiro/specs/<기능>/`이고, **버전 관리에 들어가도록 설계**돼 있습니다 — 스펙이 설명하는 코드와 같은 저장소에 둡니다.

---

## 1. Feature Specs — 워크플로를 먼저 고른다

Feature Spec은 두 워크플로 중 하나를 골라 시작합니다.

| Requirements-First | Design-First |
| --- | --- |
| 만들 시스템의 **동작을 알고** 있을 때 | 기존 기술 설계·아키텍처가 **이미 있을** 때 |
| 아키텍처가 **유연**해서 필요에 맞게 설계 가능할 때 | 지연시간·처리량·규정 준수 같은 **엄격한 비기능 요구사항**이 있을 때 |
| 고객 피드백이 이끄는 제품 기능일 때 | 특정 기술 스택으로 **프로토타이핑**할 때 |
| 기술적 제약 없이 시작할 때 | 범위를 확정하기 전 **기술적 타당성**을 탐색할 때 |

:::danger 되돌릴 수 없는 선택입니다
**스펙을 만들 때 워크플로를 골라야 하고, 이후 바꿀 수 없습니다.** 접근 방식을 바꾸려면 원하는 워크플로로 **새 Feature Spec을 만들고** 이전 스펙에서 내용을 복사해 와야 합니다.

이 문서에서 가장 비용이 큰 결정입니다. 시작 버튼을 누르기 전에 위 표를 보는 게 맞습니다.
:::

한 프로젝트에서 **둘 다 쓸 수 있습니다.** 원문이 드는 예가 실용적입니다 — Design-First로 기술적 타당성을 검증한 뒤, 전체 기능 개발용 Requirements-First 스펙을 따로 만드는 조합입니다.

### 기존 자산 가져오기

- **설계** — Design-First로 시작해 아키텍처 다이어그램(PNG·JPG)을 업로드하거나 설계 내용을 붙여넣으면 Kiro가 `design.md`로 정리하고 거기서 요구사항을 도출합니다. draw.io·Lucidchart 내보내기나 화이트보드 사진도 됩니다
- **요구사항** — JIRA·Confluence·Word에 있으면 MCP 서버로 직접 가져옵니다(로컬·원격 모두 지원). 수동이면 파일을 저장소에 복사하고 `#foo-prfaq.md Generate a spec from it`처럼 지시합니다

### 스펙을 계속 갱신하기

스펙은 **한 번 쓰고 마는 문서가 아니라 프로젝트와 함께 갱신되는 것**으로 설계돼 있습니다. 갱신 절차가 워크플로마다 다릅니다.

- **Requirements-First** — `requirements.md` 수정 → `design.md`에서 **Refine** → `tasks.md`에서 **Sync Files**
- **Design-First** — `design.md` 수정 → Kiro에게 요구사항 검증·재생성 요청 → `tasks.md`에서 **Sync Files**

## 2. Bugfix Specs — 회귀를 막는 장치

버그 설명에 넣을 네 가지가 명시돼 있습니다.

1. **재현 단계** — 버그를 트리거하는 정확한 조건
2. **현재 동작** — 지금 무슨 일이 일어나는가
3. **예상 동작** — 대신 무엇을 해야 하는가
4. **제약** — **바뀌면 안 되는** 코드나 동작

네 번째가 핵심입니다. Bugfix Spec은 수정 사항과 함께 **"변경되지 않아야 하는 동작"을 명시적으로 붙잡습니다.** 표기 형식이 정해져 있습니다.

```
WHEN [조건] THEN the system SHALL CONTINUE TO [기존 동작]
```

Kiro는 **수정과 기존 동작 보존을 모두 검증하는 속성 기반 테스트**를 만듭니다. "고쳤더니 딴 게 깨지는" 상황을 문서 형식으로 막겠다는 설계입니다.

:::warning 언제 쓰지 말라고 하는가
Bugfix Spec은 **오타·단순 로직 오류·잘 이해된 한 줄 변경에는 과합니다.** 그런 건 그냥 고치라고 합니다.

쓸 때는 따로 있습니다 — 버그가 **중요한 코드 경로**에 있을 때, **이전 수정이 회귀를 냈을** 때, **근본 원인이 바로 안 보일** 때, 규정 준수나 팀 지식을 위해 **문서가 필요할** 때.
:::

Bugfix Spec을 Feature Spec으로 **직접 전환할 수는 없습니다.** 근본 원인 분석 결과 상당한 새 기능이 필요하다고 나오면, 새 작업용 Feature Spec을 따로 만들고 Bugfix Spec은 원래 결함에 집중시키라고 합니다.

## 3. Quick Spec vs 표준 Feature Spec

둘 다 **같은 산출물**(`requirements.md`·`design.md`·`tasks.md`)을 만듭니다. 차이는 **각 단계를 검토한 뒤에 다음이 생성되는지 여부**뿐입니다 — 즉 검토 게이트의 유무입니다.

| Quick Spec | 표준 Feature Spec |
| --- | --- |
| **잘 이해된 기능**이라 출력을 믿을 때 | **낯선 영역**을 탐색할 때 |
| 빠른 프로토타이핑 — 검토보다 속도 | 요구사항·설계를 **반복**해야 할 때 |
| 표준 흐름에서 요구사항·설계를 **거의 안 고칠** 때 | 검토 게이트가 실제 가치를 더하는 **규정 준수 민감** 도메인 |
| 표준 흐름이 너무 무거워 Vibe 모드를 기본으로 써왔을 때 | 팀이 **명시적 승인 체크포인트**에서 이득을 볼 때 |

마지막 왼쪽 항목이 솔직합니다 — **"절차가 무거워서 아예 안 쓰게 되는 것"**을 실패로 인정하고 그 경우의 대안으로 Quick Spec을 제시합니다.

## 4. 요구사항 분석은 언제 돌리나

요구사항 생성 후 **Analyze Requirements**를 돌리면 논리적 불일치·모호함·상충하는 제약·누락을 잡아냅니다.

값어치를 하는 경우가 명시돼 있습니다.

- 상호작용이 중요한 **요구사항이 많은 복잡한 기능**
- 모호함의 비용이 큰 **도메인 민감 프로젝트** — 금융, 의료, 규정 준수
- 수동 검토 없이 자동 생성된 **Quick Spec 세션**

:::warning 비용도 함께 밝힙니다
전체 요구사항을 가로질러 추론하기 때문에 **몇 초가 아니라 몇 분** 걸립니다. 작거나 잘 이해된 스펙이면 **건너뛰고 설계로 바로 가라**고 합니다.
:::

## 5. 작업 실행과 동기화

- **Run all Tasks** — `tasks.md`의 작업을 한 번에 실행합니다. Kiro가 **의존성 그래프를 만들어 독립적인 것을 동시 실행**하는 웨이브로 묶습니다. 설정은 필요 없고, 미완료 필수 작업만 돌립니다
- **이미 구현된 작업이 있을 때** — `tasks.md`에서 **Sync Files**를 누르거나, 스펙 세션에서 `Check which tasks are already complete`라고 시키면 코드베이스를 분석해 완료 표시를 합니다

## 6. 스펙을 참조하고 나누기

채팅에서 `#spec` 컨텍스트 제공자로 스펙을 끌어옵니다. 참조하면 **세 파일이 전부 대화 컨텍스트에 들어갑니다.**

```
#spec:user-authentication implement task 2.3
#spec:user-authentication update the design file to include password reset flow
#spec:user-authentication does my current implementation meet the acceptance criteria for task 7.1?
#spec:user-authentication why did we choose JWT over session-based authentication?
```

마지막 예시가 흥미롭습니다 — **"왜 이 결정을 했나"를 되물을 수 있는 것**이 스펙을 파일로 남기는 이유 중 하나입니다.

### 스펙 개수와 배치

저장소당 개수 제한은 없고, **코드베이스 전체에 하나를 두려 하지 말고 기능별로 여러 개**를 만들라고 합니다.

```
.kiro/specs/
├── user-authentication/     # 로그인, 가입, 비밀번호 재설정
├── product-catalog/         # 상품 목록, 검색, 필터링
├── shopping-cart/           # 장바구니, 수량 변경, 결제
├── payment-processing/      # 결제 게이트웨이 연동, 주문 확인
└── admin-dashboard/         # 상품 관리, 사용자 분석
```

팀 간 공유는 **중앙 스펙 저장소 + Git 서브모듈/패키지 참조/심볼릭 링크** 조합을 권합니다.

vibe 대화 중에 `Generate spec`이라고 하면 그 맥락을 바탕으로 요구사항을 만들며 스펙 세션으로 넘어갑니다.

## 원문이 밝히는 경계 — 한자리에 모으면

| 대상 | 경계 |
| --- | --- |
| **워크플로 선택** | **되돌릴 수 없다.** 바꾸려면 새 스펙을 만들어 복사해야 한다 |
| Quick Spec | **잘 이해된 기능**에만. 낯선 영역에는 표준 흐름 |
| Bugfix Spec | 오타·단순 로직 오류·한 줄 수정에는 **과하다** |
| Bugfix → Feature 전환 | **직접 전환 불가.** 새 Feature Spec을 따로 만든다 |
| Analyze Requirements | **몇 분** 걸린다. 작거나 잘 이해된 스펙은 건너뛴다 |
| 스펙 하나의 범위 | 코드베이스 전체에 하나 두지 말고 **기능별로 나눈다** |

## 읽고 든 판단

여기부터는 **원문에 있는 말이 아니라 정리하며 든 생각**입니다.

- **세 도구 중 성격이 다릅니다.** Claude Code와 Codex 문서가 *에이전트와 어떻게 대화할 것인가*를 다룬다면, 이 문서는 *산출물을 어떤 형식의 파일로 남길 것인가*를 다룹니다. 프롬프트 기법이 거의 안 나오고 대신 파일 구조와 상태 전이가 나옵니다.
- **"되돌릴 수 없는 선택"이 있다는 게 이 도구의 특징입니다.** Claude Code는 체크포인트로 되돌리고 Codex는 `/fork`로 분기하는데, Kiro의 워크플로 선택은 그런 장치가 없습니다. 절차를 파일로 굳히는 대가로 유연성을 내주는 설계로 보입니다.
- **`SHALL CONTINUE TO` 표기가 이 문서에서 가장 옮겨올 만한 아이디어입니다.** "무엇을 고칠 것인가"만 적고 "무엇이 그대로여야 하는가"를 안 적는 건 도구와 무관한 흔한 실수입니다. 이건 Kiro를 안 써도 버그 리포트 형식으로 쓸 수 있습니다.

## 확인하지 못한 것

- **전부입니다.** Kiro를 설치해 돌려본 적이 없습니다.
- UI 요소 이름(**Refine**, **Sync Files**, **Run all Tasks**, **Analyze Requirements**)이 현재 버전과 맞는지 확인하지 않았습니다. 원문 내비게이션에 `IDE 1.x`·`CLI 3.0`·`2.x reference` 같은 버전 문서가 보였는데, **이 페이지가 어느 버전 기준인지는 밝혀져 있지 않습니다.**
- 속성 기반 테스트를 실제로 어떤 형태로 생성하는지 — 원문에 결과물 예시가 없습니다
- Kiro CLI에서 위 기능이 IDE와 동일하게 동작하는지 — 이 페이지는 인터페이스를 구분하지 않습니다
