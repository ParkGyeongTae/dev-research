## 모호한 바람을 어떻게 판정 가능한 지침으로 바꾸는가

저자는 추상적인 품질 요구보다 구체적이고 검사 가능한 규칙을 권합니다. 아래는 원문의 예제를 복사한 것이 아니라 **이 저장소에 적용해 만든 작성안**입니다. — [원문 — Coding Conventions Change Behavior](https://hboon.com/how-to-write-an-agents-md-that-actually-works/)

| 모호한 지침 | 이 저장소에 맞춘 작성안 | 확인할 결과 |
| --- | --- | --- |
| 검증을 잘합니다. | 문서 수정 후 저장소 루트에서 `npm run build`를 실행하고 실패·미실행이면 이유를 보고합니다. | 명령·작업 위치·출력·종료 코드·보고 |
| 출처를 신뢰할 수 있게 씁니다. | 기술적 주장 옆에 공식 원문의 제목·URL과 버전 유무를 적습니다. | 해당 주장과 원문이 실제로 대응하는지 |
| 구조를 지킵니다. | 문서를 `docs/<대분류>/<기술>/<질문>.md`에 두고 분류는 대분류의 기준에 따릅니다. | 생성 경로·질문 범위·분류 근거 |
| 커밋을 조심합니다. | 커밋·브랜치 생성·병합·푸시는 사용자가 명시적으로 요청한 범위에서 수행합니다. | 요청 범위와 실행한 Git 작업 |

```markdown title="이 저장소에 맞춘 최소 작성안 — 실제 루트 지침의 대체본이 아닙니다"
# AGENTS.md

## 작업 범위
- 커밋은 사용자가 요청한 경우에만 합니다.
- 문서는 docs/<대분류>/<기술>/<질문>.md에 둡니다.

## 문서 검증
- 문서 수정 후 저장소 루트에서 `npm run build`를 실행합니다.
- 실패하면 오류와 수정 결과를 보고합니다.
- 실행하지 못하면 이유와 남은 검증을 보고합니다.
```

**작성 판단:** 한 규칙에서 대상·행동·성공 기준·실패 처리를 찾을 수 있어야 합니다. “빌드를 실행한다”만 있으면 실패한 명령을 실행한 것으로도 작업을 마쳤다고 해석할 여지가 남습니다. 위 작성안은 명령 수행과 결과 보고를 함께 확인하도록 구성했습니다. 에이전트 행동 비교는 **미실행**입니다.

## 원문의 간결화 권고를 어디까지 적용하는가

저자는 설명을 줄이고 행동 지침을 쓰며 부정 지시로 반복 실수를 막으라고 권합니다. 조건부 지시도 잘 작동하지 않았다고 적습니다. 이는 저자의 관측이며 모든 작업에서 조건을 없애라는 근거는 아닙니다. — [원문 — Tell It What You Don't Want / Skip Explanations / What Doesn't Work](https://hboon.com/how-to-write-an-agents-md-that-actually-works/)

**이 저장소의 판단:** 적용 조건과 금지 대신 할 행동을 보존합니다. 다음 두 경우를 구분합니다.

```markdown title="적용 범위가 사라지는 축약과 조건을 유지한 작성안"
<!-- 원래 요구: 문서를 수정한 작업에서 빌드를 실행합니다. -->

<!-- 적용 범위가 넓어지는 축약 -->
- 항상 `npm run build`를 실행합니다.

<!-- 조건을 유지한 작성안 -->
- docs/ 문서를 수정했다면 저장소 루트에서 `npm run build`를 실행합니다.
- 빌드 실패 시 원인과 재실행 결과를 보고합니다.
```

첫 문장은 읽기 전용 조사까지 빌드 대상으로 만들 수 있습니다. 둘째는 원래의 적용 범위를 보존합니다. **작성 판단:** 조건문 자체보다 조건이 불명확하거나 실제 작업과 맞지 않는지를 검토합니다. 이 예시는 문장에 포함된 범위를 비교한 것이며 모델 준수율 실험이 아닙니다.

이유도 같은 기준으로 남깁니다. 이 저장소의 “README.md와 CLAUDE.md는 AGENTS.md의 심볼릭 링크이므로 일반 파일로 바꾸지 않는다”는 설명은 수정 대상을 고르는 데 필요합니다. **기존 판단을 유지합니다:** 루트 지침은 사람의 문서 구조 판단에도 쓰이므로 적용 범위를 이해하는 데 필요한 이유를 삭제하지 않습니다.

**스킬에 대한 작성 판단:** “문서 배포를 요청하면 설치된 배포 스킬을 사용한다”처럼 작업 범위와 사용 조건을 적는 편이 검토하기 쉽습니다. 스킬명만 적는 경우 실제 설치 여부와 호출 성공은 별도 확인이 필요합니다. 이 문서에서는 스킬 호출 실험을 하지 않았습니다.

## 지침과 검사 도구는 어떤 차이가 있는가

**기존 실행 기록(과거 관측):** 이전 문서에는 Prettier 3.6.2가 `if (ready) run();`에 중괄호를 추가하지 않았다는 출력이 있었습니다. 아래는 같은 명령을 **이번에 다시 실행한 출력**이며 과거 결과와 일치합니다.

```console
$ printf 'if (ready) run();\n' | npm exec --silent --yes --package=prettier@3.6.2 -- prettier --parser babel
if (ready) run();
```

종료 코드는 **0**입니다. **직접 확인:** 이 입력에서 Prettier의 성공은 “모든 `if`에 중괄호가 있다”를 뜻하지 않았습니다. 공식 설명도 포맷 재출력과 linter의 코드 품질 규칙을 구분합니다. — [Prettier vs. Linters](https://prettier.io/docs/comparison)

ESLint `curly`의 `all` 옵션은 중괄호 없는 제어문을 검사합니다. 아래에서는 저장소 설정을 읽지 않고 규칙을 명시해 **검사 규칙 자체의 동작**을 확인했습니다. — [ESLint — curly / all](https://eslint.org/docs/latest/rules/curly#all)

```console
$ printf 'if (ready) run();\n' | npm exec --silent --yes --package=eslint@9.39.1 -- eslint --no-config-lookup --stdin --stdin-filename example.js --rule 'curly: ["error", "all"]'

/Users/pgt0409/orca/workspaces/dev-research/codex/example.js
  1:12  error  Expected { after 'if' condition  curly

✖ 1 problem (1 error, 0 warnings)
  1 error and 0 warnings potentially fixable with the `--fix` option.
```

종료 코드는 **1**입니다. **직접 확인:** 같은 입력을 검사하자 중괄호 누락이 실패로 드러났습니다. 출력의 `example.js`는 표준 입력에 붙인 파일명이며 생성한 파일이 아닙니다.

**실무 판단:** AGENTS.md에는 원하는 행동과 실행할 검사를 적고 기계적으로 판정 가능한 요구는 해당 검사 설정으로도 표현합니다. “제어문에 항상 중괄호를 쓴다”를 요구한다면 formatter 성공만으로 검증을 끝내지 않습니다. 이 실험은 에이전트가 지침을 따르는지를 측정한 것이 아닙니다.

## 줄 수 대신 무엇을 유지·삭제 기준으로 삼는가

저자는 **150줄 미만**을 목표로 하고 한 절이 **20줄을 넘으면** 스킬 분리를 고려하며, 세션 후 수정 제안을 직접 검토한다고 설명합니다. 두 숫자는 경험칙입니다. — [원문 — Keep It Short / The Reflect Loop](https://hboon.com/how-to-write-an-agents-md-that-actually-works/)

**기존 기록(과거 관측):** 이전 문서는 루트 지침이 155줄이었다는 더 이른 관측과 다음 출력을 남겼습니다. 과거 원본을 복원해 줄 수를 재검증한 것은 아닙니다.

```console
$ wc -l AGENTS.md
     211 AGENTS.md
```

**이번 실행:** 현재 루트 지침을 측정한 출력입니다.

```console
$ wc -l AGENTS.md
      90 AGENTS.md
```

**해석의 한계:** 211줄에서 90줄로 관측값이 달라졌다는 사실만으로 준수율이 좋아졌다고 결론 내릴 수 없습니다. 각 시점의 작업·지침 내용·모델을 통제한 비교가 없습니다. 규칙 위반의 원인을 확인하지 못했다면 **원인 미상**으로 남깁니다.

**이 저장소의 판단:** 삭제 후보는 중복·폐기된 경로·실행할 수 없는 명령부터 찾습니다. “출처 누락을 막는다”처럼 보존할 행동을 설명할 수 있는 규칙은 길다는 이유만으로 지우지 않습니다. 스킬 분리 역시 해당 작업에서 실제로 발견하고 사용할 수 있는지 확인한 뒤 판단합니다.

## 모델이나 도구가 바뀌었을 때 어떻게 다시 평가하는가

저자는 기존 지침으로 기준 실행을 만든 뒤 소수 규칙을 제거해 같은 조건에서 반복 비교하고, 불명확하거나 퇴행하면 복원하라고 권합니다. 개별 제거가 통과해도 합친 상태를 다시 평가하며, 안전·인증·결제·개인정보·데이터 무결성 규칙은 이 제거 평가에서 제외합니다. — [원문 — Refresh AGENTS.md after model updates](https://hboon.com/how-to-write-an-agents-md-that-actually-works/)

다음은 **이 저장소에 맞춘 평가 설계안이며 미실행**입니다. 평가용 사본에서 시작 상태·모델·도구 버전·설정·작업 요청을 고정하고 기존 지침과 후보 지침을 비교합니다.

| 대표 작업 | 보존해야 할 행동 | 관찰할 실패 증상 |
| --- | --- | --- |
| 공식 문서를 읽고 기술 문서를 수정합니다. | 원문 재확인, 주장 옆 근거, 실제 출력 구분 | 출처 누락, 실행하지 않은 출력을 실행 결과로 기재 |
| 문서 빌드가 실패하는 변경을 처리합니다. | 실패 확인, 수정·재검증 또는 미해결 보고 | 실패를 생략하고 완료로 보고 |
| 문서 수정을 요청하되 Git 작업은 요청하지 않습니다. | 요청 범위 안에서 파일을 수정합니다. | 요청하지 않은 커밋·브랜치 생성 |

**평가 판단:** 답변 문구의 유사도보다 산출물·실행 명령·검사 결과·요청 범위 준수를 비교합니다. 반복 횟수와 합격 기준은 실행 전에 정하고 결과가 불명확하면 기존 규칙을 유지합니다. 이 표에는 성능 향상이나 준수율에 관한 측정 결과가 없습니다.

## 확인하지 못한 것

- **효과와 인과관계 — 미실행:** 규칙 위치·부정 표현·조건문·길이에 따른 에이전트 준수율을 비교하지 않았습니다. 원문에도 통제 실험 수치가 없습니다.
- **도구별 재현성 — 확인 필요:** 블로그에 에이전트·모델 버전이 명시되지 않아 저자의 사용 조건을 그대로 재현할 수 없습니다.
- **루트 지침의 과거 상태 — 확인 필요:** 155줄·211줄 관측 당시의 원본을 복원하지 않았습니다. 현재 90줄이라는 출력과 과거 기록을 구분했습니다.
