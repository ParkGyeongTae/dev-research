# LLM

**LLM API를 실제로 부르고 다루는 쪽**을 다룹니다. 모델을 만드는 이야기가 아니라, 남이 만든 모델을 **어떻게 제대로 쓰는가**가 주제입니다.

## 다루는 것

- 벤더별 API의 동작 — 파라미터, 프롬프트 캐싱, 레이트 리밋, 과금 단위
- 프롬프트 설계 — 무엇이 왜 효과가 있고, 어디서 무너지는가
- 툴 사용(function calling)과 에이전트 구성
- 평가 — 잘 되는지 어떻게 재는가
- 검색 증강(RAG) — 청킹·임베딩·재순위

## 경계

- **LLM을 부르는 서버 코드**(엔드포인트 설계, 인증, 타임아웃)는 [백엔드](../backend/index.md)로 갑니다. 여기서는 **무엇을 어떻게 보낼 것인가**만 다룹니다.
- **벡터 데이터베이스의 내부 동작**(인덱스 구조, ANN 알고리즘)은 [데이터베이스](../database/index.md)로 갑니다. RAG 파이프라인에서 그것을 **어떻게 쓰는가**는 여기입니다.
- **대량 배치 호출을 파이프라인에 물리는 것**은 [데이터 엔지니어링](../data-engineering/index.md)으로 갑니다.
- **GPU·추론 서버 운영**은 [인프라](../infrastructure/index.md)로 갑니다.

## 이 아래를 자르는 방식

벤더 고유의 것과 양쪽에 걸치는 것을 나눕니다. 같은 원칙을 두 벌 적어두면 **한쪽이 반드시 낡기** 때문입니다.

| 폴더 | 들어가는 것 |
| --- | --- |
| `claude-api/` · `openai-api/` | 그 벤더에만 있는 것 — 파라미터 이름과 기본값, 캐싱 방식, 레이트 리밋, 과금 단위, 모델 목록 |
| `prompt-engineering/` 등 주제 폴더 | 양쪽에 걸치는 원칙. **두 벤더 권장사항이 갈리는 지점**을 나란히 놓고 어느 조건에서 어느 쪽이 맞는지 다룹니다 |

## 공식 문서를 정리할 때 특히 조심할 것

이 영역의 문서는 다른 대분류와 두 가지가 다릅니다.

1. **버전 번호가 없습니다.** 벤더의 best practice 페이지는 판번호 없이 조용히 바뀌고 URL도 옮겨다닙니다. 그래서 버전 대신 **원문 URL · 문서 제목 · 확인 날짜** 세 개를 항상 함께 적습니다.
2. **원문에는 "안 통하는 경우"가 거의 없습니다.** 벤더 문서는 권장사항만 싣습니다. 경계와 실패 모드는 읽어서 채울 수 없고 **직접 돌려봐야** 나오므로, 확인 전까지는 "미확인"으로 남겨 둡니다 — 원문에 없는 한계를 지어내지 않습니다.
