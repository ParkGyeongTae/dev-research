# 개발 리서치 노트

현업에서 **데이터 엔지니어링**을 하면서 마주친 기술을, 쓸 줄 아는 수준에서 멈추지 않고
**왜 그렇게 동작하는지까지** 정리해 두는 개인 학습 아카이브입니다.

데이터 엔지니어링을 중심에 두되 백엔드·프론트엔드·인프라·데이터베이스·데이터 분석까지 개발 전반을 다룹니다.
읽고 끝나는 글이 아니라, 나중에 같은 문제를 만났을 때 **다시 찾아와 답을 얻는 문서**를 목표로 합니다.

---

어느 대분류에 넣을지 헷갈리는 기술은 각 대분류 페이지의 **어디로 가는가** 절에 기준을 적어 두었습니다.

## 📄 폴더 안에는 무엇이 들어가는가

**답이 나온 것만 둡니다.** 칸을 채우려고 빈 문서를 만들지 않습니다.
정해진 파일 세트는 없고, **문서 하나가 질문 하나에 답합니다.** 파일명이 그 질문을 그대로 드러냅니다 —
공식 문서 한 페이지를 정리한 것이라면 원문 주소의 slug를 그대로 씁니다.

```
docs/llm/claude-code/best-practices.md
   ← code.claude.com/docs/en/best-practices
```

## 📌 이 사이트가 지키는 것

- **개념을 먼저 세웁니다.** 사용법보다 "이게 무엇이고 왜 이렇게 생겼는가"가 앞에 옵니다. 정의는 요약해 옮기지 않고 **공식 문서의 문장을 원문·번역과 함께 인용해** 고정합니다 — 그래야 설명과 원문을 직접 대조할 수 있습니다.
- **개념마다 가장 작은 예시를 붙입니다.** 쉽게 바꾼 예시가 아니라, 그 개념이 성립하는 **가장 작은 경우**입니다. 돌릴 수 있으면 돌려서 실제 출력을 붙입니다.
- **버전을 밝힙니다.** "Kafka는 이렇게 동작한다"가 아니라 "Kafka 3.7 기준으로 이렇게 동작한다"로 씁니다. 판번호가 없는 문서가 근거일 땐 **원문 URL·문서 제목·확인 날짜**를 대신 적습니다.
- **직접 확인한 것과 읽은 것을 구분합니다.** 돌려본 결과, 공식 문서, 추측을 한 문장에 섞지 않습니다. 확인 못 한 부분은 "확인 필요"로 남겨 둡니다.
- **잘 되는 경우만 적지 않습니다.** 잘못 썼을 때 어떤 증상이 나오는지를 **그 개념을 설명하는 자리에서** 함께 씁니다 — 그게 개념이 실제로 무엇인지 보여 주는 가장 좋은 증거이기 때문입니다.
