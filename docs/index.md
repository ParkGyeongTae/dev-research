# 개발 리서치 노트

현업에서 **데이터 엔지니어링**을 하면서 마주친 기술을, 쓸 줄 아는 수준에서 멈추지 않고
**왜 그렇게 동작하는지까지** 정리해 두는 개인 학습 아카이브입니다.

데이터 엔지니어링을 중심에 두되 백엔드·프론트엔드·인프라·데이터베이스·데이터 분석까지 개발 전반을 다룹니다.
읽고 끝나는 글이 아니라, 나중에 같은 문제를 만났을 때 **다시 찾아와 답을 얻는 문서**를 목표로 합니다.

---

## 📁 둘러보기

문서는 **여섯 개의 대분류** 아래에 기술별로 쌓입니다. 왼쪽 메뉴에서 골라 들어가면 됩니다.

| 대분류 | 다루는 것 |
| --- | --- |
| [백엔드](./backend/index.md) | 애플리케이션 서버·API·런타임 (Spring, FastAPI, JVM, gRPC …) |
| [프론트엔드](./frontend/index.md) | 브라우저에서 도는 것 (React, TypeScript, 번들러 …) |
| [데이터 엔지니어링](./data-engineering/index.md) | 스트리밍·배치·오케스트레이션·저장 포맷 (Kafka, Spark, Airflow, Iceberg …) |
| [데이터 분석](./data-analytics/index.md) | 분석용 변환·라이브러리·지표 (dbt, pandas, BI …) |
| [인프라](./infrastructure/index.md) | 컨테이너·클라우드·IaC·관측성 (Kubernetes, Terraform, Prometheus …) |
| [데이터베이스](./database/index.md) | 저장 엔진의 내부 동작과 튜닝 (PostgreSQL, ClickHouse, Redis …) |

**기술 하나가 폴더 하나**입니다 — 예를 들어 Kafka는 `data-engineering/kafka/` 아래에 모입니다.
어느 대분류에 넣을지 헷갈리는 기술은 각 대분류 페이지의 **경계** 절에 기준을 적어 두었습니다.

## 📄 기술 폴더 안에는 무엇이 들어가는가

**답이 나온 것만 둡니다.** 칸을 채우려고 빈 문서를 만들지 않습니다.
정해진 파일 세트는 없고, **문서 하나가 질문 하나에 답합니다.** 파일명이 그 질문을 그대로 드러냅니다 —
공식 문서 한 페이지를 정리한 것이라면 원문 주소의 마지막 조각을 그대로 씁니다.

```
docs/llm/claude-code/best-practices.md
   ← code.claude.com/docs/en/best-practices
```

문서마다 다루는 것은 다르지만, 아래 셋은 빠지면 안 됩니다.

| 담아야 할 것 | 왜 |
| --- | --- |
| **경계** — 이 기술이 **안 맞는** 상황 | 장점만 있는 문서는 홍보 자료지 리서치가 아닙니다 |
| **검증 근거** — 버전을 밝힌 출처, 또는 직접 돌려본 기록 | 나중에 스스로 다시 확인할 수 있어야 합니다 |
| **실패 모드** — 잘못 쓰면 어떤 증상이 나타나는가 | 같은 문제를 다시 만났을 때 찾아오는 곳이기 때문입니다 |

---

## 📌 이 사이트가 지키는 것

- **버전을 밝힙니다.** "Kafka는 이렇게 동작한다"가 아니라 "Kafka 3.7 기준으로 이렇게 동작한다"로 씁니다 — 버전이 바뀌면 답도 바뀝니다.
- **직접 확인한 것과 읽은 것을 구분합니다.** 돌려본 결과, 공식 문서, 추측을 한 문장에 섞지 않습니다.
- **출처를 남깁니다.** 공식 문서·소스 코드·KIP/PEP 같은 1차 자료를 우선하고, 블로그를 근거로 쓸 땐 그렇게 밝힙니다.
- **모르는 건 모른다고 씁니다.** 확인 못 한 부분은 "확인 필요"로 남겨 둡니다 — 나중에 채우기 위해서입니다.
- **경계를 씁니다.** 이 기술이 **안 맞는 상황**이 빠진 문서는 홍보 자료지 리서치가 아닙니다.
