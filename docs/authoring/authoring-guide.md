# 문서 작성 가이드

이 저장소의 **폴더 구조·명명 규칙·파일별 역할·작성 규칙**의 마스터 문서입니다.
[`AGENTS.md`](https://github.com/ParkGyeongTae/dev-research/blob/main/AGENTS.md)의 행동 지침과 어긋나는 내용이 있으면 **이 문서가 우선**입니다.

---

## 1. 문서를 어디에 둘 것인가

이 저장소는 문서를 성격에 따라 세 곳으로 나눕니다. **판단은 아래 순서로 합니다.**

```
이 문서는 특정 제품/기술 하나를 다루는가?
├─ 아니오 → 두 곳 이상에서 인용되는 개념인가?
│           ├─ 예   → docs/concepts/
│           └─ 아니오 → docs/notes/<연도>/
└─ 예 → 그 기술을 깊이 팔 계획이 있는가? (또는 이미 노트가 3편 이상 쌓였는가)
        ├─ 예   → docs/topics/<카테고리>/<기술>/
        └─ 아니오 → docs/notes/<연도>/
```

| 위치 | 단위 | 들어가는 것 |
| --- | --- | --- |
| `docs/topics/<카테고리>/<기술>/` | 기술 하나 = 폴더 하나 | 정해진 파일 세트(§3)를 채우는 깊은 리서치 |
| `docs/notes/<연도>/` | 문제 하나 = 파일 하나 | 삽질 기록, 단발성 확인, 여러 기술에 걸친 메모 |
| `docs/concepts/` | 개념 하나 = 파일 하나 | 제품에 종속되지 않는 이론 |
| `docs/glossary.md` | 용어 한 줄 정의 | 두 문서 이상이 쓰는 용어 |

### 승격 규칙

- **노트 → 기술 리서치**: 같은 기술 노트가 3편 이상 쌓이면 폴더로 승격합니다. 옮긴 뒤 원래 노트는 **지웁니다** — 같은 내용이 두 곳에 남으면 한쪽이 반드시 낡습니다.
- **기술 문서 → 개념 정리**: 한 기술 폴더의 `03_concepts.md`에 쓴 개념을 다른 문서가 인용하게 되면 `docs/concepts/`로 올리고, 원래 자리엔 링크만 남깁니다.
- **미리 승격하지 않습니다.** 두 번째 인용이 실제로 생겼을 때 옮깁니다.

## 2. 명명 규칙

- **폴더·파일명은 소문자 영문 + 하이픈**: `data-engineering/`, `kafka/`, `consistency-models.md`
- **기술 폴더명은 공식 표기를 소문자로**: `kafka`(❌ `apache-kafka`), `postgresql`(❌ `postgres`), `kubernetes`(❌ `k8s`) — 검색으로 찾을 때 헷갈리지 않게 축약어 대신 정식 명칭을 씁니다.
- **기술 폴더 안의 파일은 번호 접두사 고정**(§3). 번호를 건너뛰거나 새 번호를 만들지 않습니다.
- **단편 노트는 `<주제>-<무엇>.md`**: `jvm-gc-tuning.md`, `psql-explain-reading.md`. 날짜는 파일명에 넣지 않습니다 — 연도 폴더와 `*작성일*` 줄이 이미 담고 있습니다.
- **문서 제목(H1)과 내비게이션 표기는 한국어**를 씁니다. 제품명·표준 용어(Kafka, WAL, p99 등)는 원문 그대로 둡니다.

## 3. 기술 문서 폴더의 파일별 역할

`docs/topics/<카테고리>/<기술>/` 아래에 둡니다. 빈 뼈대는 [`template/topic/`](./template/topic/00_summary.md)에 있습니다.

| 파일 | 역할 | 반드시 담아야 하는 것 |
| --- | --- | --- |
| `00_summary.md` | **자기완결 요약**. 나머지를 안 읽어도 그림이 서야 함 | 한 문단 정의 · 언제 쓰고 언제 안 쓰는지 · 핵심 개념 3~5개 · 가장 자주 겪는 함정 |
| `01_overview.md` | 이 기술이 **어떤 문제**를 풀려고 나왔는가 | 없던 시절의 방식 · 대안 기술과의 비교 · 안 맞는 상황 |
| `02_architecture.md` | 내부 구조와 데이터 흐름 | 구성 요소 · 요청/데이터 하나가 흐르는 경로 · 어디에 상태가 저장되는가 |
| `03_concepts.md` | 이 기술 전용 핵심 개념 | 개념별 정의와 **왜 필요한지** |
| `04_hands-on.md` | 직접 돌려본 기록 | 실행 환경(버전·OS·리소스) · 재현 가능한 명령 · **실제 출력** · 알게 된 것 |
| `05_operations.md` | 실무 운영 | 배포 형태 · 봐야 할 지표 · 튜닝 파라미터와 트레이드오프 |
| `06_pitfalls.md` | 틀리기 쉬운 지점 | 증상 → 원인 → 해결 · 왜 헷갈리는지 |
| `07_references.md` | 근거 목록 | 공식 문서(버전 명시) · 설계 문서(KIP/PEP/RFC) · 소스 코드 위치 · 참고한 글 |

**해당 없는 파일은 만들지 않습니다.** 대신 `00_summary.md` 맨 아래에 "`04_hands-on` 없음 — 아직 직접 돌려보지 않음" 처럼 **왜 없는지 한 줄** 남깁니다. 빈 껍데기 문서는 "정리했다"는 착각만 만듭니다.

## 4. 숫자와 주장을 다룰 때 반드시 지키는 것

이 저장소에서 가장 많이 틀리는 다섯 가지입니다.

1. **버전을 밝힌다.** 동작을 설명하는 모든 문장은 버전에 매여 있습니다. "Kafka는 …" 대신 "Kafka 3.7 기준 …"으로 씁니다. 버전을 확인 못 했으면 "확인 필요"로 남깁니다.
2. **직접 확인한 것 / 문서에서 읽은 것 / 추측을 구분한다.** 셋을 한 문장에 섞지 않습니다. 돌려본 것은 `04_hands-on.md`에 출력과 함께, 읽은 것은 출처 링크와 함께, 추측은 **"추측:"** 을 붙여 씁니다.
3. **성능 수치엔 조건을 붙인다.** "10배 빠르다"는 조건 없이는 의미가 없습니다. 하드웨어·데이터 크기·동시성·측정 방법을 함께 쓰지 못하겠으면 그 수치는 쓰지 않습니다.
4. **기본값과 설정값을 구분한다.** "이 옵션은 켜져 있다"가 제품 기본값인지, 회사 클러스터의 설정인지, 내 로컬 실험 설정인지 밝힙니다.
5. **비유는 비유라고 밝힌다.** "Kafka는 로그 파일 같은 것"류의 설명은 이해를 돕지만, 어디까지 맞고 어디서 깨지는지 함께 쓰지 않으면 나중에 잘못된 모델로 굳습니다.

### 출처 우선순위

**공식 문서(버전 명시) · 소스 코드 > 설계 문서(KIP/PEP/RFC/논문) > 메인테이너의 글·컨퍼런스 발표 > 개인 블로그·Stack Overflow**

낮은 순위 자료만 근거일 땐 그렇게 밝힙니다. 자료끼리 갈리면 한쪽을 고르지 말고 **둘 다 적고 어느 쪽이 어떤 조건에서 맞는지**를 `06_pitfalls.md`에서 다룹니다.

## 5. 새 기술 폴더를 추가하는 절차

1. 카테고리를 고릅니다(`docs/topics/index.md`의 표). 없으면 새로 만듭니다 — 폴더만 만들면 내비게이션에 자동으로 잡힙니다(`.pages`의 `...` 토큰).
2. `docs/authoring/template/topic/`의 파일을 새 폴더로 복사합니다.
3. 채울 수 있는 파일부터 채우고, 채울 수 없는 파일은 **지웁니다**(§3).
4. 새 용어가 생겼으면 `docs/glossary.md` 또는 `docs/concepts/`를 먼저 갱신합니다.
5. `*작성일*` 줄을 오늘 날짜로 갱신합니다.
6. `uv run mkdocs build`로 `unrecognized relative link` 경고가 늘지 않았는지 확인합니다.
7. `grep -rn "> ⚠️" docs/topics/<카테고리>/<기술>/`가 비어야 발행 준비가 끝난 것입니다 — 템플릿 지침 블록이 남아 있으면 안 됩니다.

새 카테고리를 만들었다면 `docs/topics/index.md`의 카테고리 표에도 한 줄 추가합니다.

## 6. 문서는 부분 수정하지 않고 다시 만든다

"개선/최신화해 달라"는 요청도 **해당 폴더를 지우고 현재 템플릿으로 새로 만드는 방식**으로 처리합니다.
부분 수정하면 눈에 띄는 절만 고쳐지고 옛 구조가 남습니다.

지우기 전에 **다시 구하기 어려운 것**만 추려 옮깁니다.

- `04_hands-on.md`의 실행 기록 — 직접 돌려본 결과라 웹에서 다시 못 구합니다
- `06_pitfalls.md`의 실무에서 겪은 사례
- 이 저장소에서 내린 판단(왜 이 기술을 쓰기로/안 쓰기로 했는지)

지운 내용은 git 히스토리에 남습니다.
