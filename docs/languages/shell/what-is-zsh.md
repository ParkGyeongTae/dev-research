# zsh란 무엇인가 — bash와 문법이 같아 보이지만 의미가 다른 셸

맥의 기본 로그인 셸이 zsh이므로, 터미널에서 명령을 짜 맞춘 뒤 그대로 `.sh` 파일에 옮기는 일이 자연스럽게 일어납니다.
그런데 **zsh는 bash와 문법이 비슷할 뿐, 같은 문법에 다른 의미를 준 곳이 있습니다.** 문법이 달랐다면 오류가 나서 알았을 텐데, 문법이 같으니 **오류 없이 다른 값이 나옵니다.**
이 문서는 그 "같은 문법, 다른 의미"가 어디인지를 개념으로 잡고 실제로 돌려서 확인합니다.

## 실행 환경

아래 실행 기록은 모두 이 환경에서 **직접 돌린 결과**입니다.

## 1. 무엇인가

공식 사이트가 자기를 소개하는 문장입니다.

> a shell designed for interactive use, although it is also a powerful scripting language
>
> — [zsh.org](https://www.zsh.org/) (확인: 2026-09-06)

**"대화형 사용을 위해 설계됐다"가 먼저 나오는 것**이 zsh의 성격을 그대로 보여줍니다. 스크립트 언어이기도 하지만 무게중심이 다르고, 뒤에 나올 설계 선택들도 이 우선순위에서 나옵니다 — 터미널에서 사람이 치기 편한 쪽을 골랐고, 그 선택이 POSIX 계열의 관례와 갈립니다.

**이 문서는 언어로서의 zsh만 다룹니다.** 프롬프트 구성·자동완성·설정 프레임워크 같은 대화형 환경 이야기는 주제가 아니고, **그것이 스크립트를 깨뜨리는 지점**(§5)만 짚습니다.

### 버전

이 머신에 깔린 것과 공개된 최신 릴리스입니다.

```console
$ /bin/zsh --version
zsh 5.9 (arm64-apple-darwin24.0)
```

공식 배포처(SourceForge)에는 5.9 이후 판이 올라와 있습니다. 파일 존재를 직접 확인한 결과입니다 (조회: 2026-09-06).

```console
$ for v in 5.9 5.9.1 5.9.2; do
    curl -s -o /dev/null -w "%{http_code}\n" -L "https://sourceforge.net/projects/zsh/files/zsh/$v/zsh-$v.tar.xz/download"
  done
200
200
200
```

**5.9.1·5.9.2가 존재합니다**(디렉터리 게시일 2026-07-12). 다만 같은 시점에 zsh.org 첫 화면은 5.9를 현재 릴리스로 안내하고 있었습니다 — **두 자료가 갈리므로 어느 쪽이 최신 안정판인지는 확정하지 않습니다. 확인 필요.**

## 2. 가장 중요한 차이 — 변수를 단어로 쪼개지 않습니다

bash·dash를 포함한 POSIX 계열 셸에서, 따옴표 없는 변수 확장은 값을 그대로 내놓지 않습니다. **공백 기준으로 쪼개진 뒤** 명령에 전달됩니다(단어 분리). **zsh는 기본적으로 쪼개지 않습니다** — 변수 하나가 값 하나로 남습니다.

같은 스크립트를 네 셸에서 돌렸습니다.

```bash title="split.sh"
files="a.csv b.csv c.csv"
count=0
for f in $files; do
  count=$((count + 1))
done
echo "루프 반복 횟수: $count"

path="/data/my report.csv"
[ -n "$path" ] && set -- $path
echo "인자 개수: $#"
```

```console
$ for s in /bin/sh /bin/bash /bin/dash /bin/zsh; do
    printf '%-11s -> ' "$(basename $s)"; $s split.sh | tr '\n' ' '; echo
  done
sh          -> 루프 반복 횟수: 3 인자 개수: 2
bash        -> 루프 반복 횟수: 3 인자 개수: 2
dash        -> 루프 반복 횟수: 3 인자 개수: 2
zsh         -> 루프 반복 횟수: 1 인자 개수: 1
```

**두 방향 모두 실무에서 사고가 됩니다.**

- **위쪽(반복 횟수 3 → 1)**: 공백으로 구분한 목록을 순회하는 흔한 관용구가 zsh에서는 **한 번만 돕니다.** 파일 3개를 처리해야 하는데 1개만 처리하고 **종료 코드 0으로 정상 종료**합니다 — 오류도 경고도 없습니다. 알림도 재시도도 걸리지 않고, 다음 단계에서 데이터가 비어 있는 것으로 나중에 발견됩니다.
- **아래쪽(인자 2 → 1)**: 공백이 든 경로 하나가 bash에서는 **두 개로 쪼개집니다.** 이건 bash 쪽의 고전적인 버그이고, zsh의 동작이 오히려 안전합니다.

즉 zsh가 더 낫거나 못한 게 아니라 **의미가 다릅니다.** 그리고 어느 쪽이든 **따옴표를 제대로 쓰면**(`"$path"`, 목록은 배열로) 두 셸에서 같은 결과가 나옵니다. 단어 분리에 의존하는 코드만이 셸을 옮길 때 깨집니다.

## 3. 배열 인덱스가 1부터 시작합니다

```console
$ /bin/bash -c 'arr=(첫째 둘째 셋째); echo "arr[1]=${arr[1]}  개수=${#arr[@]}"'
arr[1]=둘째  개수=3
$ /bin/zsh  -c 'arr=(첫째 둘째 셋째); echo "arr[1]=${arr[1]}  개수=${#arr[@]}"'
arr[1]=첫째  개수=3
```

**같은 `${arr[1]}`이 bash에서는 두 번째 원소, zsh에서는 첫 번째 원소입니다.** 원소 개수는 양쪽 다 3으로 같습니다.

§2와 같은 성격의 차이입니다 — 문법은 글자 하나 다르지 않고, 오류도 나지 않고, **값이 하나씩 밀립니다.** 배열로 파일 목록이나 파티션 날짜를 다루다가 셸을 옮기면 스크립트는 정상 종료하고 **결과만 틀립니다.**

## 4. bash보다 앞서는 것도 있습니다

맥에 한정된 이야기지만 실무에서는 이게 더 자주 걸립니다.

```console
$ for s in /bin/sh /bin/bash /bin/dash /bin/zsh; do
    printf '%-6s -> ' "$(basename $s)"; $s -c 'declare -A m; m[k]=v; echo "지원: ${m[k]}"' 2>&1 | head -1
  done
sh     -> /bin/sh: line 0: declare: -A: invalid option
bash   -> /bin/bash: line 0: declare: -A: invalid option
dash   -> /bin/dash: 1: declare: not found
zsh    -> 지원: v
```

**맥의 zsh 5.9는 연관 배열을 지원하고, 같은 맥의 bash 3.2.57은 지원하지 않습니다.**

그래서 **로컬 안에서도 셸이 갈립니다.** 터미널(zsh)에서 시험할 때는 되던 것이, `#!/bin/bash`를 붙여 파일로 만드는 순간 안 됩니다. "같은 컴퓨터인데 왜"라는 반응이 나오는 지점이고, 원인은 컴퓨터가 아니라 셸입니다.

`[[ ]]`는 양쪽 다 됩니다.

```console
$ /bin/zsh -c '[[ "abc" == a* ]] && echo "지원"'
지원
```

## 5. 실무에서 어디에 쓰이는가

### 대화형 기본값이라는 자리

macOS의 기본 로그인 셸이 zsh입니다.

```console
$ echo $SHELL
/bin/zsh
```

그래서 데이터 엔지니어가 zsh를 쓰는 시간의 대부분은 **터미널에서 명령을 치는 시간**입니다. 스크립트를 zsh로 짜는 경우는 상대적으로 드뭅니다 — 배포 대상(컨테이너·CI·리눅스 서버)에 zsh가 기본 설치돼 있다고 가정할 수 없기 때문입니다. `#!/bin/zsh` 스크립트를 zsh 없는 이미지로 보내면 셔뱅 해석 단계에서 실행 자체가 실패합니다.

### 그래서 실제로 걸리는 지점

1. **터미널에서 조립한 명령을 `.sh`로 옮길 때** — §2·§3·§4의 차이가 여기서 드러납니다. 특히 §2·§3은 오류 없이 결과만 달라지므로, **"돌아간다"가 "맞게 돌아간다"를 뜻하지 않습니다.**
2. **`.zshrc`에 넣은 것이 스크립트에는 없을 때** — 별칭·함수·`PATH` 설정은 대화형 셸에만 적용되므로, 터미널에서 되던 명령이 크론이나 CI에서 `command not found`가 됩니다. §4가 "셸이 달라서" 생기는 문제라면 이건 "설정이 안 읽혀서" 생기는 문제이고, 증상이 비슷해 헷갈립니다.
3. **다른 사람이 이어받는 스크립트** — 읽는 사람이 bash를 전제하면 §2·§3을 잘못 읽습니다. 코드가 아니라 독해가 틀립니다.

**결론(의견): 대화형은 zsh를 쓰되, 배포되는 스크립트는 `bash`나 POSIX `sh`로 짜고 셔뱅을 명시하는 편이 안전합니다.** 로컬 검증도 그 셸로 해야 의미가 있습니다.

> 2번의 `.zshrc` 미적용과 `#!/bin/zsh`의 배포 실패는 구조에서 따라 나오는 설명이며, **이 저장소에서 컨테이너로 재현하지 않았습니다 — 확인 필요.**
