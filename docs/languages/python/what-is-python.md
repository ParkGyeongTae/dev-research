# Python이란 무엇인가 — 타입 힌트와 GIL을 오해하지 않기

데이터 엔지니어에게 Python은 "이미 아는 언어"입니다. 그래서 오히려 두 가지를 잘못 알고 있기 쉽습니다 —
**타입 힌트가 무엇을 보장하는지**, 그리고 **GIL이 무엇을 막는지**입니다. 둘 다 개념을 설명한 뒤 실제로 돌려서 확인합니다.

**실행 환경**: Python 3.13.2 (macOS, Darwin 24.6.0, Apple M4 Pro 14코어). 아래 출력은 모두 이 환경에서 실제로 돌린 것입니다(2026-09-06).

## 1. 무엇인가 — 명세가 아니라 참조 구현

Java나 JavaScript와 달리 Python에는 **표준화 기구가 승인한 언어 명세가 없습니다.**
[Python Language Reference](https://docs.python.org/3/reference/index.html)(확인: 2026-09-06)가 있지만 문서 스스로 이것이 완전한 명세는 아니라고 밝히고 있고, 실질적 기준은 **참조 구현인 CPython의 동작**입니다. 언어 변경은 **PEP**(Python Enhancement Proposal)로 제안되고 논의됩니다.

이 차이가 실무에서 걸리는 지점은 "Python"이라고 말할 때 대상이 갈린다는 것입니다. 명세가 기준이면 구현이 여럿이어도 같은 동작을 기대할 수 있지만, 참조 구현이 기준이면 **구현을 바꾸는 순간 기준이 흔들립니다.**

| 구현 | 성격 |
| --- | --- |
| **CPython** | 참조 구현. 아래 모든 실행 기록은 이것 기준 |
| **PyPy** | JIT 구현. 순수 Python 코드에서 빠르지만 C 확장 호환이 갈림 |
| **Jython / GraalPy 등** | 다른 런타임 위의 구현 |

그리고 실제로는 선택지가 좁습니다. PySpark·pandas·NumPy처럼 **C 확장에 의존하는 라이브러리**를 쓰면 사실상 CPython에 묶입니다. C 확장은 CPython의 내부 구조에 맞춰 빌드되기 때문입니다 — 이 사실이 §4의 GIL 이야기와 §6의 버전 충돌 이야기로 이어집니다.

## 2. 어떻게 실행되는가

`소스(.py)` → **컴파일** → `바이트코드(.pyc)` → **평가 루프**입니다. "인터프리터 언어"라는 말과 달리 컴파일 단계가 있고, 다만 그 결과가 기계어가 아니라 바이트코드입니다.

```console
$ python3 -c "import dis; dis.dis(compile('n = 1 + 2', '<s>', 'exec'))"
  0           RESUME                   0

  1           LOAD_CONST               0 (3)
              STORE_NAME               0 (n)
              RETURN_CONST             1 (None)
```

`1 + 2`가 `LOAD_CONST 3`으로 바뀌어 있습니다 — 컴파일 시점에 상수 접기가 일어납니다.

다만 여기까지가 컴파일러가 하는 일의 거의 전부입니다. 나머지는 **평가 루프가 바이트코드를 하나씩 해석하면서** 진행되고, 그 해석 비용이 매 연산에 붙습니다. 그래서 밀리초 단위 지연이 걸린 경로에서는 인터프리터 오버헤드와 GC 타이밍이 꼬리 지연에 그대로 드러납니다. Python이 "글루 언어"로 쓰이고 무거운 계산은 C 확장이나 다른 엔진으로 내려보내는 관행이 여기서 나옵니다.

## 3. 타입 힌트는 런타임에 강제되지 않습니다

가장 자주 오해되는 지점입니다. 타입 힌트는 **주석에 가깝고, 인터프리터는 그것을 검사하지 않습니다.**

```python title="hint.py"
def add(a: int, b: int) -> int:
    return a + b

print(add("가", "나"))
print(add.__annotations__)
```

```console
$ python3 hint.py
가나
{'a': <class 'int'>, 'b': <class 'int'>, 'return': <class 'int'>}
```

`int`를 요구한 함수에 문자열 두 개를 넣었는데 **오류 없이 `"가나"`가 나옵니다.** 두 번째 줄이 힌트의 정체를 보여 줍니다 — 힌트는 `__annotations__`에 **데이터로** 남아 있을 뿐이고, 함수를 부를 때 그것을 보는 코드는 없습니다.

그래서 힌트를 달아 놓은 것과 검사하는 것은 다른 일입니다. 타입 힌트가 실제로 무언가를 잡으려면 **mypy·pyright 같은 별도 검사기를 CI에서 돌려야** 합니다. 검사기를 강제로 넣지 않은 대규모 코드베이스에서는 힌트가 장식으로 남고, 시간이 지나면 실제 코드와 어긋난 채로 남습니다.

### 그래서 오류는 그 코드 줄에 실행이 닿아야 드러납니다

```console
$ python3 -c 'n: int = 0
n = "문자열"
print(n + 1)'
  File "<string>", line 3, in <module>
    print(n + 1)
          ~~^~~
TypeError: can only concatenate str (not "int") to str
```

`n: int` 선언이 있는데도 문자열 대입이 **그냥 통과했고**, 오류는 `n + 1`을 실제로 실행할 때 났습니다.

파이프라인에서 이것이 특히 아픈 이유는 **어느 코드가 늦게 실행되는지가 정해져 있기 때문**입니다. 월말에만 타는 분기, 에러 처리 경로, 재시도 경로가 그렇습니다. 그런 자리의 타입 오류는 월말에, 혹은 장애가 났을 때 처음 드러납니다.

방어책은 둘입니다. 검사기를 CI에 넣는 것, 그리고 **외부에서 들어온 데이터는 힌트가 아니라 실행되는 검증 코드로 확인하는 것**입니다.

## 4. GIL — 무엇을 막고 무엇을 막지 않는가

GIL(Global Interpreter Lock)은 **한 인터프리터 안에서 파이썬 바이트코드를 한 번에 하나의 스레드만 실행하게** 하는 잠금입니다. §2에서 본 평가 루프를 한 번에 하나만 돌리는 잠금이라고 보면 됩니다.

기본 빌드에는 켜져 있고, 인터프리터에게 직접 물어볼 수 있습니다.

```console
$ python3 -c "import sys, sysconfig; print('Py_GIL_DISABLED =', sysconfig.get_config_var('Py_GIL_DISABLED')); print('_is_gil_enabled =', sys._is_gil_enabled())"
Py_GIL_DISABLED = 0
_is_gil_enabled = True
```

### 실측 — 스레드를 늘려도 안 빨라집니다

CPU 바운드 작업(순수 파이썬 루프 4,000만 회 × 4건)을 스레드와 프로세스로 각각 돌렸습니다.

**측정 조건**: Python 3.13.2 기본 빌드(GIL 켜짐), macOS Darwin 24.6.0, `os.cpu_count()` = 14. 작업은 `for i in range(40_000_000): s += i * i`. `time.perf_counter()` 기준. 2회 반복.

```console
$ python3 gil.py
python 3.13.2 | GIL enabled = True
CPU count: 14
스레드 1개 (작업 4건)                    3.47s
스레드 4개 (작업 4건)                    3.36s
프로세스 4개 (작업 4건)                   0.98s

$ python3 gil.py     # 2회차
스레드 1개 (작업 4건)                    3.50s
스레드 4개 (작업 4건)                    3.40s
프로세스 4개 (작업 4건)                   0.98s
```

**스레드를 1개에서 4개로 늘려도 시간이 줄지 않습니다**(3.47s → 3.36s). 코어는 14개인데 파이썬 바이트코드는 한 번에 하나만 돌기 때문입니다. 프로세스 4개는 약 3.5배 빨라졌습니다(프로세스 기동 비용이 포함된 수치라, 작업이 길어지면 비율은 더 올라갑니다).

이 결과에서 알아 둘 것은 숫자보다 **증상의 모양**입니다. 스레드를 늘렸는데 오류도 경고도 나지 않고 **아무 변화가 없습니다.** 튜닝했다고 생각하고 넘어가기 쉽고, 바꾸기 전후를 실제로 재지 않으면 드러나지 않습니다.

### 단, 이건 "순수 파이썬 CPU 바운드"에만 해당합니다

GIL이 무엇을 막는지 정확히 잡아 두면 반대 경우도 정리됩니다. GIL은 **파이썬 바이트코드의 동시 실행**을 막는 것이지 동시성 전반을 막는 게 아닙니다.

- **I/O 대기** — 네트워크·디스크 대기 중에는 GIL이 풀립니다. API 호출이나 DB 쿼리를 스레드로 병렬화하는 것은 유효합니다.
- **GIL을 놓는 C 확장 안에서의 계산** — NumPy 같은 라이브러리의 일부 연산은 계산 구간에서 GIL을 반납합니다. 어떤 연산이 그런지는 **라이브러리·버전마다 다르므로 개별 확인이 필요합니다 — 확인 필요.**

그래서 실무의 결론은 "Python은 병렬이 안 된다"가 아니라 **"순수 파이썬으로 도는 CPU 바운드 구간은 스레드로 풀리지 않는다"**입니다. 그 구간은 보통 프로세스로 나누거나(메모리와 직렬화 비용을 냅니다), C 확장·JVM 엔진·SQL 엔진으로 내려보냅니다.

### free-threaded 빌드 (PEP 703 / PEP 779)

GIL을 뺀 빌드는 **Python 3.14에서 공식 지원 단계**가 됐습니다.

> PEP 779: Free-threaded Python is officially supported
>
> — [What's New In Python 3.14](https://docs.python.org/3.14/whatsnew/3.14.html) (확인: 2026-09-06)

같은 문서 기준으로 3.14의 free-threaded 빌드는 **단일 스레드 코드에서 5~10%의 성능 손해**를 봅니다(3.13의 실험 단계보다 개선된 수치).

다만 "공식 지원"이 "지금 파이프라인에 쓰면 된다"는 뜻은 아닙니다. §1에서 본 대로 데이터 스택은 C 확장 덩어리이고, C 확장이 free-threaded 빌드에서 동작하려면 각각 대응해야 합니다.
**이 저장소에서 free-threaded 빌드를 돌려본 적은 없습니다 — 위 내용은 전부 공식 문서에서 읽은 것입니다.**

## 5. 버전 — 지금 무엇을 쓰는가

Python은 **매년 10월에 한 번 기능 릴리스**를 냅니다. 각 버전은 릴리스 후 약 5년간 지원됩니다.

| 버전 | 최초 릴리스 | 상태 | 지원 종료 |
| --- | --- | --- | --- |
| 3.13 | 2024-10-07 | bugfix | 2029-10 |
| 3.14 | 2025-10-07 | bugfix (최신 안정) | 2030-10 |
| 3.15 | 2026-10-01 (예정) | prerelease | 2031-10 |

[Python Developer's Guide — Status of Python versions](https://devguide.python.org/versions/) 기준(확인: 2026-09-06).
같은 표에서 **3.9는 2025-10-31에 EOL**, 3.10은 2026-10에 EOL 예정입니다. 3.10에 묶인 파이프라인이 있다면 한 달 남았습니다.

3.14의 주요 변경 중 실무에 걸릴 만한 것([What's New In Python 3.14](https://docs.python.org/3.14/whatsnew/3.14.html), 확인: 2026-09-06):

- **PEP 649/749 — 어노테이션 지연 평가.** 어노테이션이 즉시 평가되지 않고 `annotationlib`으로 조회합니다. §3에서 본 `__annotations__`를 런타임에 읽는 라이브러리(데이터 검증·ORM 계열)의 동작에 영향을 줄 수 있습니다.
- **PEP 750 — 템플릿 문자열(`t'...'`).** 정적 부분과 보간 부분을 분리해 다룰 수 있습니다.
- **PEP 734 — `concurrent.interpreters`.** 서브 인터프리터를 표준 라이브러리에서 제공합니다.
- **PEP 768 — `sys.remote_exec()`.** 프로세스를 멈추지 않고 디버거를 붙일 수 있습니다.

> 추측: PEP 649의 어노테이션 지연 평가는 어노테이션을 런타임에 읽어 동작을 결정하는 라이브러리에서 가장 문제가 될 가능성이 높습니다. **어떤 라이브러리가 실제로 깨지는지는 확인하지 않았습니다 — 확인 필요.**

## 6. 실무에서 어디에 쓰이는가

### 설문 수치

PSF와 JetBrains가 함께 낸 [Python Developers Survey 2024](https://lp.jetbrains.com/python-developers-survey-2024/)(2024년 10~11월 조사, 약 200개국 30,000명 이상 응답. 확인: 2026-09-06) 기준입니다.

**주 용도**(하나만 선택): 웹 개발 23%, 머신러닝 13%, 데이터 분석 10%, 학술 연구 8%, 교육 8%, **데이터 엔지니어링 7%**, DevOps 6%.

**관여 영역**(주·부 합산): 데이터 분석 49%, 웹 개발 48%, 머신러닝 42%, **데이터 엔지니어링 33%**, 웹 스크래핑 28%.

두 수치의 차이가 Python의 성격을 보여줍니다. **"주 업무가 데이터 엔지니어링"인 사람은 7%지만, 데이터 엔지니어링에 Python을 쓰는 사람은 33%입니다.** Python은 한 영역의 전용 언어가 아니라 여러 영역에 걸쳐 얇게 깔리는 접착제에 가깝습니다.

**설문 자료의 한계**: 자기선택 편향이 있습니다(PSF/JetBrains 채널로 모집). 코드 줄 수나 시스템 규모가 아니라 응답자 비율입니다.

### 데이터 엔지니어의 실제 사용처

- **오케스트레이션** — Airflow DAG, Prefect, Dagster의 작성 언어
- **처리** — PySpark, pandas, Polars, DuckDB 바인딩
- **수집·연동** — API 클라이언트, 커스텀 커넥터, 스키마 검증
- **글루 코드** — 배포 스크립트, 데이터 품질 체크, 사내 CLI

**PySpark를 쓸 때 성능이 어디서 나오는지는 §4와 함께 봐야 합니다.** DataFrame API로 작성한 연산은 실행 계획으로 JVM에 넘어가 JVM에서 처리되므로 GIL과 무관합니다. 반면 파이썬으로 작성한 UDF는 파이썬 워커 프로세스에서 실행되며 데이터가 JVM과 파이썬 사이를 오갑니다.

> 위 문단의 구조 자체는 널리 알려진 것이지만, **직렬화 비용이 실제로 얼마나 되는지는 이 저장소에서 측정한 적 없습니다 — 확인 필요.** 사용 중인 Spark 버전의 공식 문서로 확인해야 합니다.

### 배포에서 걸리는 것 — 인터프리터와 C 확장은 한 몸입니다

§1에서 C 확장이 CPython에 묶여 있다고 했는데, 그 결속은 **버전 단위**로 이뤄집니다. C 확장은 특정 파이썬 버전의 ABI로 빌드되므로, 인터프리터를 올리면 휠을 다시 받아야 하고 **해당 버전 휠이 아직 없으면 소스 빌드로 떨어지거나 설치가 실패합니다.** 새 파이썬 버전이 나온 직후(매년 10월 전후)에 특히 자주 겪습니다.

그래서 "내 노트북에서는 됐는데"가 다른 언어보다 자주 발생합니다. 걸리는 것이 코드가 아니라 **인터프리터 버전 + C 확장 ABI + 시스템 라이브러리의 조합**이기 때문입니다. 배포 환경을 통제할 수 없는 곳에서 Python이 까다로운 이유가 이것입니다.

> 위 두 문단은 널리 알려진 동작이지만 **이 저장소에서 재현 기록을 남기지 않았습니다 — 확인 필요.**
