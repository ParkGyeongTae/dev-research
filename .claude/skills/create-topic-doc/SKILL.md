# 기술 문서 작성 (신규 · 재생성 공통)

## 언제 쓰나

- **신규**: "<기술> 정리해줘", "<기술> 문서 만들어줘", "<기술> 파보자"
- **재생성**: "<기술> 문서 개선해줘 / 최신화해줘 / 버전 올라갔으니 다시 봐줘"
- **대상 아님**: 문제 하나짜리 기록 → `docs/notes/<연도>/`에 단일 파일로 (스킬 불필요)

개선 요청도 **재생성으로 처리한다** — 부분 수정하면 눈에 띄는 절만 고치고 템플릿이 바뀐 뒤에도 옛 구조가 남는다. 지운 내용은 git 히스토리에 남는다.

## 작업 방식

기술 폴더 하나는 **한 대화에서 끝까지** 만든다. 아래를 응답에 복사해 두고 단계마다 표시한다.

```
[ ] 1. 범위·버전 확정
[ ] 2. 배치 결정 (topic인지 note인지 / 카테고리)
[ ] 3. 기존 내용 보존 (재생성일 때만)
[ ] 4. 근거 수집 (공식 문서·설계 문서·소스)
[ ] 5. 문서 작성
[ ] 6. 마무리 검증
```

---

## 1. 범위·버전 확정

먼저 사용자에게 확인한다. **추측해서 진행하지 않는다.**

- **기준 버전** — "어느 버전 기준으로 쓸까요?" 확인 못 하면 최신 안정 버전을 쓰되 문서에 그렇게 밝힌다. 버전 없이 동작을 서술하는 문서는 만들지 않는다.
- **직접 돌려볼 수 있는가** — 로컬/사내에서 실행 가능한지. **불가능하면 `04_hands-on.md`를 만들지 않는다.** 실행하지 않고 그럴듯한 출력을 지어내는 것이 이 저장소에서 가장 심각한 오염이다.
- **이미 아는 부분** — 사용자가 실무에서 쓰고 있는 기술이면 어디까지 알고 있는지 묻는다. 아는 것을 다시 설명하는 데 분량을 쓰지 않기 위해서다.

## 2. 배치 결정

`docs/authoring/authoring-guide.md` §1의 판단 흐름을 따른다. 요약:

- 제품/기술 하나를 **깊이 팔 계획**이 있으면 → `docs/topics/<카테고리>/<기술>/`
- 문제 하나로 끝나면 → `docs/notes/<연도>/<주제>-<무엇>.md` (이 스킬을 종료하고 파일 하나만 쓴다)
- 제품 종속이 아닌 이론이면 → `docs/concepts/`

카테고리는 `docs/topics/index.md`의 표에서 고른다. 맞는 게 없으면 새로 만들고 **그 표에 한 줄 추가**한다.
폴더명은 공식 표기의 소문자(`kubernetes`, not `k8s`).

## 3. 기존 내용 보존 (재생성일 때만)

폴더를 지우기 전에 **웹에서 다시 못 구하는 것**을 먼저 읽어 별도로 옮겨 둔다.

- `04_hands-on.md` 전체 — 직접 돌려본 기록
- `06_pitfalls.md` 중 "직접 겪음"으로 표시된 항목
- 이 저장소에서 내린 판단 (왜 이 기술을 쓰기로/안 쓰기로 했는지)

옮길 것을 확보한 뒤 폴더를 지우고 템플릿에서 다시 시작한다.

## 4. 근거 수집

**기억으로 쓰지 않는다.** 아래 순서로 실제 자료를 확인한다.

1. **해당 버전의 공식 문서** — 기본값·설정 이름·API는 반드시 여기서 확인한다. 버전이 다르면 답이 달라진다.
2. **설계 문서** (KIP / PEP / RFC / 논문) — "왜 이렇게 설계했는가"는 여기에만 있다. `01_overview.md`·`02_architecture.md`의 핵심 근거.
3. **소스 코드** — 문서에 없는 동작을 확인해야 할 때만.
4. **블로그·발표** — 위에서 못 찾은 것만. 이것만 근거인 주장은 본문에 그렇게 밝힌다.

자료끼리 갈리면 한쪽을 고르지 말고 **양쪽을 적고 조건을 구분**한다.

**수집하면서 다음 세 가지를 따로 기록해 둔다** — 문서의 뼈대가 된다.

- 이 기술이 **안 맞는 상황** (없으면 문서가 홍보물이 된다)
- 이름 때문에 헷갈리는 지점
- 버전 사이에 바뀐 동작

## 5. 문서 작성

`docs/authoring/template/topic/`을 복사해 채운다. 파일별 역할은 `authoring-guide.md` §3.

작성 순서는 **02 → 03 → 01 → 06 → 05 → 07 → 00** 을 권한다. 구조를 먼저 파악해야 개요를 제대로 쓸 수 있고, 요약은 나머지가 끝난 뒤에야 정확해진다. `04`는 실행한 시점에 쓴다.

지키는 것:

- 동작을 서술하는 문장에 **기준 버전**을 매단다.
- **확인 / 읽음 / 추측**을 구분한다. 추측엔 `추측:` 을 붙인다.
- 성능 수치엔 하드웨어·데이터 크기·측정 방법을 함께 쓴다. 못 쓰면 그 수치를 뺀다.
- 채울 수 없는 파일은 **만들지 않고**, `00_summary.md`에 왜 없는지 한 줄 남긴다.
- 다른 기술 설명으로 번지면 멈추고 `docs/concepts/`나 별도 폴더로 뺀다.

## 6. 마무리 검증

`AGENTS.md`의 "작업을 마치기 전에" 7개 항목을 **실제로 실행한다.** 최소한 아래 셋은 명령을 돌려 확인한다.

```bash
grep -rn "> ⚠️" docs/topics/                      # 비어야 함 (템플릿 지침 잔존 확인)
grep -rn --include='*.md' "YYYY-MM-DD" docs/topics/  # 비어야 함 (작성일 미갱신 확인)
uv run mkdocs build 2>&1 | grep -i "warn"          # 링크 경고가 늘지 않았는지
```

보고할 때 **확인한 것과 확인하지 못한 것을 구분**해서 말한다. 공식 문서로 검증하지 못하고 기억에 기댄 부분이 있으면 숨기지 말고 그렇게 말한다.
